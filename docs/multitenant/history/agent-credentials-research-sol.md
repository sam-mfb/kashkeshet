# Agent credentials for kkt

Researched 2026-11-01. Confidence labels refer to documented behavior; proposed kkt designs are engineering judgments, not tested integrations.

## 1. Accepted practice and maturity

**Yes: give each workload its own identity and a short-lived, least-privilege grant; keep the credential that can create broader grants outside it. High confidence.** OAuth supplies mature components, but there is no universally deployed “avatar delegation” profile across MCP clients and identity providers.

[RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html) is a Standards Track token-exchange protocol supporting delegation, requested resources/scopes, and an `act` actor claim. It does **not** automatically impose attenuation, propagate revocation, or link child lifetime to parent lifetime. Those are authorization-server policies. Exchanging a human token inside a worker still exposes human authority.

**A narrower access token is not necessarily a narrower renewable grant. High confidence.** [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html) explicitly says a refresh token returned when narrowing resources during code redemption remains bound to the full original grant. Entra [refresh tokens](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens) span resources/tenants where that client/user has permission. Its v2 `aud` is the [API application's client ID](https://learn.microsoft.com/en-us/entra/identity-platform/access-token-claims-reference), not an arbitrary identifier URI. Separate API registrations improve audience separation; they do not confine a broadly authorized refresh token. Require a separate restricted grant or workload identity, with server-enforced ceilings on every renewal/exchange.

**Proof of possession is standardized. High confidence.** [DPoP, RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html), binds tokens to a key and signs individual requests; public-client refresh tokens are key-bound too. [mTLS, RFC 8705](https://www.rfc-editor.org/rfc/rfc8705.html), supports certificate-bound access tokens. Neither prevents misuse by an agent already able to use the key. Neither automatically delivers immediate revocation. OAuth's [security BCP](https://www.rfc-editor.org/rfc/rfc9700.html) recommends sender constraints and requires public-client refresh-token replay protection through sender constraints or rotation.

**Agent-specific work remains emerging. High confidence on status, medium on interoperability.** IETF WG drafts include [WIMSE AIMS](https://datatracker.ietf.org/doc/draft-ietf-wimse-aims/) and OAuth [ID-JAG](https://datatracker.ietf.org/doc/draft-ietf-oauth-identity-assertion-authz-grant/); neither is a published RFC. OpenID's [AIIM whitepaper](https://openid.net/wp-content/uploads/2025/10/Identity-Management-for-Agentic-AI.pdf) is analysis, while [AuthZEN drafts](https://openid.net/openid-foundation-advances-authorization-for-the-agent-era-with-new-authzen-working-group-drafts/) concern authorization interfaces, not a turnkey credential protocol. MCP has optional [client-credentials and enterprise-managed extensions](https://modelcontextprotocol.io/extensions/auth/overview); its [roadmap](https://blog.modelcontextprotocol.io/posts/mcp-roadmap/) still calls for finalizing DPoP and an agent delegation path. Core [2026-07-28 authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) alone does not establish per-worker identity. The [TypeScript v2 SDK](https://ts.sdk.modelcontextprotocol.io/v2/api/%40modelcontextprotocol/client/client/dpop.html) has DPoP machinery; SDK support does not establish application support.

## 2. Concrete designs

### A. External authorization server issues an avatar grant

Human approves one avatar/swarm through a trusted web control plane. A confidential backend exchanges or provisions a restricted grant at the external AS. Tokens identify the avatar and authorizing human, target kkt, expire quickly, and carry a fixed permission ceiling. Workers receive only that grant's credentials. kkt maps the authenticated principal to tenant/avatar/swarm and checks current membership on every operation. Scope challenges must never let that principal upgrade into a human/admin grant.

**Protects:** privilege separation, attribution, centralized issuance and renewal controls. Sam's theft requirement additionally requires DPoP or certificate binding; bearer-only A is insufficient. **Does not:** protect a readable sibling key; guarantee immediate JWT revocation without introspection/current-state checks. Revoking the upstream human session must explicitly stop downstream grants; token exchange does not promise this.

**Vendor practice, high confidence:** [Okta](https://developer.okta.com/docs/guides/ai-agent-token-exchange/resourceserver/main/) documents agent token exchange, MCP resources and Cross App Access. [Auth0](https://auth0.com/blog/the-many-faces-of-oauth2-token-exchange/) offers custom RFC 8693 exchange, with developer-defined validation; [DPoP availability](https://support.auth0.com/center/s/article/availability-of-demonstrating-proof-of-possession-dpop-in-auth0) is tier-dependent. [Keycloak](https://www.keycloak.org/securing-apps/token-exchange) has supported standard exchange, with provider-specific restrictions.

Keycloak defaults exchange refresh-token issuance off, lacks `resource` support there, and does not cascade access-token revocation. Google's [Credential Access Boundaries](https://docs.cloud.google.com/iam/docs/downscoping-short-lived-credentials) demonstrate shipped downscoping, but support Cloud Storage only. Neither is a generic plug-in kkt solution.

[WorkOS Agent Registration](https://workos.com/docs/authkit/agent-registration) documents user claiming, agent subjects, authorizer claims, refresh and revocation validation. Separate [Agent Auth](https://workos.com/docs/authkit/agent-blueprints) documents permission ceilings, revocable sessions and short-lived bearer tokens; enablement is required and its stated scope is first-party agents. These are close prior art, not proof that arbitrary Codex/Claude workers get DPoP. kkt still owns avatar/swarm policy, onboarding and renewal integration; obtain provider confirmation for this deployment.

**Client support, medium confidence:** [Claude Code](https://code.claude.com/docs/en/mcp) and [Codex](https://learn.chatgpt.com/docs/extend/mcp) document OAuth, bearer headers and credential helpers. Helpers operate per connection/refresh, not per HTTP request, so cannot implement DPoP by supplying one cached proof. [Claude.ai](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp) documents cloud-hosted OAuth connections. [ChatGPT](https://developers.openai.com/plugins/build/auth) documents bearer OAuth and an OpenAI-managed mTLS certificate identifying ChatGPT; this is not a customer-controlled per-avatar certificate or documented RFC 8705 token binding. It excludes customer certificates and machine-to-machine grants. I found no documented, dependable native DPoP configuration for these four clients; treat support as unverified, not categorically absent.

### B. Isolated per-avatar MCP bridge with workload identity

Run each agent with a dedicated stdio-to-remote-MCP bridge. The bridge acquires AS-issued avatar tokens and performs DPoP or mTLS itself. Provision its workload identity from an isolated supervisor; human/blueprint credentials stay in a different trust boundary. Agents access only their bridge; the bridge exposes no general token-minting/signing service.

**Protects:** native clients need no DPoP implementation; tokens/keys can stay outside model-controlled execution. **Does not:** stop authorized malicious avatar actions or protect sibling bridges reachable by the same unrestricted OS account. kkt builds bridge lifecycle and avatar mapping, using existing OAuth/DPoP libraries rather than inventing authentication.

**Vendor practice:** [Entra Agent ID](https://learn.microsoft.com/en-us/entra/agent-id/agent-identities) has agent principals and accountable sponsors, with privileged blueprints acquiring tokens. [Third-party integration](https://learn.microsoft.com/en-us/entra/agent-id/configure-third-party-agents) documents sidecars/federation. [Google](https://docs.cloud.google.com/mcp/authenticate-mcp) documents attested agent identities and certificate-bound Google access tokens; these are platform-specific, not generic kkt tokens. [AWS AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/get-workload-access-token.html) binds user/workload identity, but its workload access tokens authorize first-party AgentCore services only. Confidence high on these limits, medium on fit. Local CLI clients support stdio; cloud Claude.ai/ChatGPT cannot launch this local bridge.

**Established analogues, high confidence:** [Kubernetes bound service-account tokens](https://kubernetes.io/docs/concepts/security/service-accounts/) have audience/expiry and object lifecycle binding; online TokenReview detects deletion whereas offline verification waits for expiry. [GitHub App installation tokens](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys) narrow repositories/permissions and expire after one hour. [CI OIDC federation](https://docs.github.com/en/actions/concepts/security/openid-connect) obtains temporary cloud credentials without permanent cloud secrets. Adopt their separation of issuer authority from workload credentials.

## 3. Where not to roll our own

Use an established AS for grants, exchange, renewal, revocation and keys; audited libraries for JWT/DPoP/mTLS and discovery. kkt remains a resource server. A kkt mint-code/token service would introduce an additional credential issuer, regardless of its name.

[Macaroons](https://research.google/pubs/macaroons-cookies-with-contextual-caveats-for-decentralized-authorization-in-the-cloud/) and [Biscuit](https://www.biscuitsec.org/docs/why-biscuit/) offer attenuation but are bearer credentials by default; Biscuit leaves revocation infrastructure external. [UCAN](https://github.com/ucan-wg/spec) provides cryptographic delegation/invocation and revocation specifications. These are project protocols, not a universally supported OAuth/MCP profile. They leave IdP linkage, revocation distribution and capability semantics to integration. Confidence high: useful prior art, unnecessary complexity for one central kkt authority.

## 4. Recommendation

Choose A with a proven external AS and sender constraints; use B to supply those constraints for CLI clients. Prototype one provider's complete restricted-renewal/revocation path before committing, including attempted broader refresh/exchange, sibling impersonation and owner disablement. If a hosted client cannot satisfy binding, it cannot meet the full requirement today. Confidence high in the architecture, medium in present product interoperability.

The hard requirement also needs OS isolation: separate users or enforced sandbox/VM boundaries, private files, restricted IPC and no shared human credential/browser access. [DPoP §11.4](https://www.rfc-editor.org/rfc/rfc9449.html#section-11.4) explicitly excludes security guarantees when adversaries execute in the client's context. tmux sessions, distinct environment variables, and keys readable by the same UID do not establish avatar confinement. Confidence high. No token standard can supply the missing execution boundary.
