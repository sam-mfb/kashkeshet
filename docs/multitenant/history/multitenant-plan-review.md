1. **P0 — A worker still has a route across swarms and into sibling avatars.** Where: §§2, 6, 8; steps B–D. `/mcp` receives user sign-in, keeps unrestricted `register(swarm)`, and allows owner reclaim without a recovery code. A worker can register again in another available swarm, or reclaim a sibling and read its memory. The server cannot establish that a caller registering again has never heard anything. Today's MCP transport is stateless (`src/app.rs::mcp_transport`); registration and reclaim have no current-avatar binding (`src/mcp.rs`). Separate URLs alone also do not prevent reuse of a user's credential at `/mcp-user` or `/mcp-admin`. Suggested change: define endpoint-specific credential grants, bind ordinary calls to the granted owner and avatar, and keep owner reclaim on the user surface. If workers must be confined, use a narrowly scoped bootstrap grant for registration that cannot be reused to gain another swarm. Otherwise explicitly promise isolation between avatar credentials, not between agent processes or their accumulated knowledge. Preserve today's key-mode behavior separately.

2. **P1 — Login cannot ship before isolation and scoped web access.** Where: §11, steps B, C, D. B creates distinct users and personal swarms, but user pages arrive in C and the visibility rule becomes live in D. That leaves B with either unusable login or cross-user reads. Today's `store::channel_ids` returns all open channels; `Rules::list_agents` reads the global list. `web::Gate` returns only yes/no and pages share one `Source`. Suggested change: make every personal-swarm read/write check, user-scoped web source, and login-to-principal binding a prerequisite of B. D should enable sharing, not first enable isolation. Give each step a two-user acceptance test and an explicit description of what those users can do.

3. **P1 — Scope the live feed and authorization lifetime, not just page queries.** Where: §§4–6; steps B–E. `src/web/real.rs::live` forwards the global event stream, including message bodies and closed-channel metadata; `src/web/mod.rs::events` keeps it open after the initial admission check. Scoped lists would not fix this leak. Authentication also precedes later database operations; waits retain an `Agent` and do not reauthenticate (`rules/auth.rs`, `rules/messages.rs`). Suggested change: require scoped subscriptions with permission checks before delivery, revoke or terminate streams on access loss, and check mutable authorization in the transaction performing a change. Test removal during an open SSE feed, wait, and concurrent registration/write, not only a subsequent fresh request.

4. **P1 — Define a complete deactivation transition before implementing cascades.** Where: §§3–4, 8–10; step D. “Kept, hidden, unusable” does not say whether memberships disappear, channel ownership is cleared, channels become hidden, or owners retain historical web access. Today `Operator::revoke` preserves memberships and ownership; `Rules::hide_agent` refuses channel owners; `unregister` removes memberships and clears ownership with notices (`rules/operator.rs`, `rules/administration.rs`, `store/sqlite.rs::hide_agent`). Reusing hide would let an owner block a required access-loss cascade. Suggested change: specify one atomic forced-deactivation operation covering credentials, memberships, channel ownership, notices, memory and held lane. State whether it is irreversible, what rejoining a group does, who can read retained memory/history, and what remains visible for historical message authors. Keep `unregister`'s permanent meaning explicit.

5. **P1 — Access loss needs effective grants and parent-object transitions.** Where: §4; §§5 and 9 user removal/org suspension. Removal from one group must not deactivate an avatar if another shared group, or swarm ownership, still grants access. User deletion, role loss, group deletion, swarm-owner removal and org suspension are not specified; the personal swarm supposedly cannot be deactivated even when its user is removed. Suggested change: compute access from the union of current grants, then cascade only on a true loss. Add a transition table for all these operations, including owned shared swarms, personal avatars, credentials, lanes, channels and resumption. Reject removal of the last administrator unless a replacement or server recovery path exists.

6. **P1 — Per-org handles require new internal identities, not just a uniqueness index.** Where: §§3, 8, 10; steps A and E. `agents.name` is today's primary key. Memberships, messages, channel creators/owners/note editors, memory and lookups refer to it (`migrations/0001`, `0007`, `0008`, `0012`, `0013`, `0019`). Waiting and send-rate state also use bare handles (`rules/waiting.rs`, `rules/rate.rs`). Two orgs with `crisp-crane` would collide or address the wrong data if only registration became scoped. Suggested change: introduce an immutable internal AvatarId, a case-insensitive unique `(org_id, handle)`, and migrate every reference and in-memory key. Resolve tool handles within the authorized scope. Preserve message IDs and search indexes. Test duplicate handles across two orgs through memory, reclaim, ownership, waits and administration.

7. **P1 — The proposed contracts do not yet enforce the claimed scope boundary.** Where: §5 and step A. An org-admin method accepting any `OrgId` can still be called with another org's ID; distinct traits alone do not make that a compile error. Today's admin functions and `Actor::Human`/`Who::Admin` are globally privileged, and aggregate reads such as `admin_activity` bypass per-channel decisions (`rules/admin.rs`, `rules/access.rs`). Suggested change: construct a private, scope-bound capability from the authenticated principal; methods derive the org/user scope from it rather than accept arbitrary scope IDs. Retain runtime relationship checks and scope SQL before counts/pagination. Inventory all admin reads, memory, notes, search, previews, activity and writes. Do not claim compile-time protection from forged or stale authorization that still needs runtime checks.

8. **P1 — Channel authority for humans is ambiguous and may bypass channel ownership.** Where: §5 User permissions and §9 user/swarm pages. “Act on their channels with the owner's powers” could mean any channel one of the user's avatars joined. That would let a newly joined member's user hide a channel or remove its actual owner. It is also unclear whether a swarm owner sees all closed channels or other users' memory. Suggested change: spell out read, membership and ownership powers separately for avatar owner, channel owner, swarm owner and org admin. A simple default is that a user's channel-changing authority is derived from an owned avatar that currently has the required membership/ownership. Any broader authority must be explicit in both human pages and agent instructions.

9. **P1 — Avatar transfer contradicts permanent ownership and leaves old credentials alive.** Where: §3 “owned for good,” §4 transfer, and the deferred login page. Checking the new owner's swarm access does not define who may transfer, whether the old owner's token/recovery code remain valid, or which user can read the existing memory. A personal avatar cannot change owners while staying in the old owner's unshareable personal swarm. Suggested change: defer transfer and keep ownership immutable for this release. If transfer is required, define its authorization and atomic credential invalidation, access to historical memory, announcement changes, and same-org restriction. Explicitly refuse personal-swarm transfers rather than suggesting they work like shared ones.

10. **P1 — The migration silently changes existing revoked avatars and misses mode conversion.** Where: §10; step A. Existing revoked avatars remain visible and keep memberships/ownership; mapping them to hidden deactivated avatars changes more than the notice sender and two null fields. Existing hidden/unregistered avatars have different state again. Keyless loopback installs also exist (`Admission::Open`), but only key mappings are described. Finally, enabling login after migration gives each human a new personal swarm while every old avatar/channel belongs to the synthetic default user; there is no safe ownership-claim path. Suggested change: preserve old states unless a specific compatibility break is approved, define keyless behavior, and specify an explicit administrative mapping for the default user when login is enabled. Test populated databases containing revoked owners, hidden channels, ownerless operator channels, memory, lane versions, old token/recovery hashes and old message IDs. Also test successive A→B→C→D→E upgrades, not just one final schema opening v0.7.0.

11. **P1 — Existing admin announcement tools lose their authority without a replacement contract.** Where: §§5–8, 10; step E and §11's introductory sentence. `/mcp-admin` currently has `get_server_announcement` and `set_server_announcement` (`src/mcp_admin.rs`); the plan gives that surface org-admin powers but reserves server announcements for server admins, whose only surface is web. Silently making the old setter edit an org announcement would contradict the promise to retain the server field and meaning. Suggested change: keep legacy key-mode authority explicit, add separately named org-announcement tools, and define the permission error or additional grant for server-announcement operations in login mode. Correct “moves ... the announcement under the org”: existing server announcements are expressly supposed to stay server-wide. Record all tool/behavior changes in the contract tests and approval scope.

12. **P2 — Human-created channels have no creator swarm.** Where: §§3–4, 8, 10. “Always its creator's swarm” works only for avatar creation. Web and admin tools already create ownerless channels as `operator`, and users explicitly have no avatar (`web/source.rs::create_channel`, `migrations/0012_operator_channels.sql`). Suggested change: give human/admin channel creation an authorized target swarm, defaulting to the personal swarm for legacy key mode. Validate every initial member against it. Preserve existing ownerless channels and define who can administer them after migration.

13. **P2 — Lane scoping needs its own migration and CLI selection rules.** Where: §§7, 10–11; step E. Lanes and version references currently use global names; immutable version triggers and an avatar's pinned version must survive the change (`migrations/0016`–`0018`). Tokenless `list_lanes` needs an authenticated org context. `kkt lanes import/export` operates directly on the database with no org argument; `--retire-missing` must not affect other orgs. Suggested change: preserve existing lanes, retired lanes and pinned versions in the default org; use a scoped lane identity throughout. Add explicit org selection for multi-org CLI operations while preserving the old single-org default. Test equal lane names in different orgs, history, reclaim, and scoped retirement. Do the analogous scope selection for `kkt agent revoke <handle>`.

14. **P2 — Swarm creation has conflicting authorities.** Where: §§1, 6, 12–13 versus step D. The decisions repeatedly say humans create swarms only on the web and reject agent creation; D explicitly permits creation through `/mcp-user`. Suggested change: follow the stated decision and omit creation from `/mcp-user`, or obtain an explicit revised decision that a delegated user agent may create swarms. List precisely which “manage my swarms” operations that endpoint exposes. Also specify stable SwarmIds and naming rules: registration cannot safely identify one of two same-named swarms using a display name alone.

15. **P2 — Strict non-discovery conflicts with shared namespaces and counters.** Where: §§2, 4, 8 and handle-uniqueness rationale in §12. Within one org, registration's `handle_taken` reveals that a handle exists in another personal/shared swarm even though it must otherwise be indistinguishable from absent. Global monotonic message IDs also expose activity outside the caller's visible channels. Suggested change: define the promised privacy boundary precisely and document these metadata exceptions if acceptable. If swarm-level non-discovery is absolute, scope handles to swarms and reconsider external cursors; do not claim strict non-discovery while retaining these observable shared values.

16. **P2 — Step F changes the model rather than merely extending sharing.** Where: §11 F against §§3–5 and §8. Groups are defined as belonging to one org, org-admin reads are org-scoped, lanes are org-local and handles unique only within an org. A shared cross-org channel can contain two identical handles; an output marker does not disambiguate input handles for add/remove/transfer or sender filters. Channel-owning org, foreign memory visibility, lane visibility, consent withdrawal and either org's suspension are unspecified. Suggested change: move F to a separate future design rather than claim it ships as the next independent step. Before enabling it, specify qualified identity inputs, the channel's owning scope, each admin's reach, and withdrawal semantics.

17. **P2 — Remote tenants still share unbounded or global resource budgets.** Where: §§5–6 and §11 B/E. Registration has one global bucket and active-avatar cap (`rules/rate.rs`, `rules/agents.rs`); deactivation allows more registrations while retained rows and messages continue accumulating. A tenant can prevent another from registering or consume the shared disk even with correct row isolation. Suggested change: before untrusted remote use, define small per-user/org limits for registrations, active avatars and retained storage alongside the server cap. Keep single-user defaults unchanged and avoid a configurable quota framework until needed.

18. **P2 — Fixed roles do not need a mutable role-definition layer.** Where: §5, step A, and §2's proposed principle. The plan has exactly three built-in roles and no custom roles, yet makes their permission mapping data and proposes three complete contracts before any second user exists. Suggested change: start with fixed permissions in code, stored role assignments, and small scope-bound interfaces for the actual operations. Add editable role definitions only with a concrete use case. State the security property as enforcing granted scopes; “agents may not orchestrate several swarms” is a workflow restriction the server cannot enforce on an external process and should not become a general design principle.
