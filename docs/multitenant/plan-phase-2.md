# Plan, phase 2: kkt-pro

Status: plan, 2026-11-08, by kkt-mt-plan for Sam. The companion of `plan-phase-1.md`, which holds the fixed points, the rules that bind every step and the list of what is superseded; this document does not repeat them. Phase 2 starts whenever Sam chooses, after phase 1. Its open questions (section 9) are deferred by Sam. Nothing here is implemented.

## 1. Goal and shape

Build kkt-pro, a private product on kashkeshet's crates: orgs, users, roles, groups and grants above the swarms; login through the org's provider for humans and kkt's own authorization server for avatars; the hard lines of roadmap section 2 enforced in one place; a one-way upgrade from a kkt file. Key mode is unchanged throughout. The roadmap's steps 3 to 6 are done here, on pro's own tables and crates, in their order.

**Pro's crates:** `kkt-pro-rules` (orgs, users, roles, groups, grants, transitions, `allows`), `kkt-pro-store`, `kkt-pro-web` (users, groups, swarms, grants, consent and approval pages; composition across swarms), `kkt-pro-mcp` (`/mcp-user`, the org admin tools), `kkt-pro-server`, `kkt-oidc`, `kkt-avatar-auth`, `kkt-mock-issuer` (dev only), and the `kkt-pro` program. Each new third-party library is wrapped in one crate with `real` and `testing` features and listed in its `third-party-features.txt`. kkt-pro's own CLAUDE.md lists them.

**Order:** 2.0 runs ahead of and alongside the rest, since each later step needs some of it. 2.1 to 2.4 are in sequence. 2.5 is optional, any time after 2.2. 2.6 runs alongside 2.1 to 2.5.

## 3. Step 2.1: login and grants (roadmap step 3)

| Part | What lands |
|---|---|
| **Humans sign in** | `kkt-oidc`: `TokenVerifier` and `PageSignIn` behind `real`, a fake verifier behind `testing`. kkt is a resource server for humans, never their authorization server: tokens for `/mcp-admin` (and later `/mcp-user`) come from the org's provider (Entra, Okta custom server, WorkOS; Auth0 and Keycloak same code path, unsupported at first) and are checked per roadmap 8.7: signature by a key of the configured issuer, pinned algorithms, `iss`, `aud` per endpoint (or the one shared audience with the role check separating the two human endpoints), `exp`, `nbf`, token kind, no application-only grants. The page sign-in transaction of 8.7: short-lived, single use, browser-bound `SameSite=Lax` cookie, state, nonce, PKCE, fixed callback, same-origin return, id_token audience = page client ID, separate code from access-token verification. Identity promise narrow: a documented claim stable across page and resources (Entra `oid`, WorkOS and Okta `sub`); mismatch refused, never linked by email. Discovery and keys cached; refresh on an unknown key ID bounded. |
| **Avatars get credentials** | `kkt-avatar-auth`: a standard OAuth 2.1 authorization server for avatar tokens only, audience `/mcp` only, library or sidecar (open question 1); it decides nothing about approval and asks through a contract kkt-pro-server adapts. Metadata, PKCE S256, CIMD and dynamic registration, RFC 9207 `iss` on success and errors, resource indicators, the authorization code grant with the consent page, the device grant with the approval page and `slow_down`, opaque access tokens (`avatar_access_token_lifetime`, default 15 minutes), rotated refresh tokens with reuse detection, stop at the grant deadline (`avatar_grant_lifetime`, default 30 days). Tokens hashed, from the injected `Entropy`. `kkt register --token-file` and `kkt reclaim --handle` run the device grant into a private token file that `kkt watch` reads and refreshes (which program: open question 3). No `kkt login`; the command never holds a human credential. |
| **The grant** | One record per avatar in kkt-pro-store: owner (user, keyed by issuer and subject), org, swarm, avatar, permissions (`mcp`, optionally `avatars:create` with count and expiry), deadline, revocation state, parent grant, client, run. Every `/mcp` request checks current state: grant, avatar, swarm, owner and org active, owner has access to the swarm; the `token` parameter, if given, must name the grant's avatar. A new grant for an avatar revokes the old one and ends its waits. Revocation cascades to children and wakes open waits and feeds, which recheck and end. `create_avatar` under `avatars:create`: same swarm, `mcp` only, deadline no later than the parent's, count spent atomically, never passed on, credentials returned once. In login mode: `register` without a grant refused, recovery codes not issued, recovery-code `reclaim` refused, no access, web or admin key, no fallback between modes. |
| **Approval pages** | Consent and device-approval pages in kkt-pro-web on kkt's origin, following `Change`: form `POST` with the viewer's form token, origin checked, `frame-ancestors 'none'`. The human types the device code while signed in; the swarm is chosen server-side from the swarms the human has access to; agent-supplied text is advisory, escaped and marked as the requester's claim; a pending request binds issuer, org, client, suggested name, deadline and nonce immutably; approval adds the user, swarm, avatar and permissions and is consumed once in the transaction that writes the grant (one file, so one transaction); codes expire in minutes; confirmation is a button naming the swarm and avatar. Rate limits as `Limits` fields in pro's struct: pending requests per user, approvals per minute, unauthenticated requests per minute, per-user sends and active avatars; today's `sends_per_minute` stays per avatar and `registrations_per_minute` per server. |
| **Roles and pages** | kkt-pro-rules: `allows` returning a private, scope-bound capability (user: user ID; org admin: org ID; server admin: nothing); the three contracts take the capability and no scope IDs; storage queries by the capability's scope before counting or paging; relationship checks on every call inside the transaction. Three fixed roles in code, assignments stored, no custom roles. Every existing tool and page checks a role through `allows`, so a non-admin sign-in inherits nothing of today's operator. Pro's `Identify` maps a bearer to (swarm, `Avatar`) for `/mcp`, and a signed-in user to `Operator { words }` or `Reader` in each swarm for the human surfaces. A human changes a channel through one active owned avatar that satisfies the whole action; facts of two avatars are never combined. Avatar details split from memory (owner and org admins only). Deactivation via the core's operation, with notices naming who did it by role or avatar, never by human name. Administrative changes store the authenticated user ID and admin agent name through the change-record hook. Minimal user pages: my avatars and their grants, consent and approval, revoke, deactivate, sign out; the org admin's user list with remove and roles. Users created at first sign-in; one org bound to the issuer; the bootstrap server admin from the config line by issuer and subject (or verified email, never on Entra), consumed once, bound to that subject, lockout recovery by a new line. The shared space of roadmap step 3 is the org's one swarm, which the core already has. |
| **Recheck and revocation promises** | kkt keeps the page sign-in's provider refresh token on the server and refreshes it every `identity_recheck_interval` (default 1 hour); `invalid_grant` suspends the user's avatar grants and ends their waits; no success for `identity_staleness_max` (default 24 hours) suspends until one; a provider that gives no refresh token leaves the grant deadline as the bound, and the documentation names it. Sign-out ends the page session only. Provider events not consumed at first. The web session (default 12 hours) is kkt's own window and outlives the provider token by design. Same-OS-account siblings can take each other's avatars, never the human's power; the documentation says so. |
| **Needs** | 2.0 (extras, hook, OpenID Connect mode, migration sets); the authorization-server decision (open question 1); the checks of roadmap section 13 (open question 5). |
| **Verified by** | Through HTTP with `kkt-mock-issuer` started in-process by pro's `tests/common`, not only seeded rule calls: three roles each confined on every tool and page; a test per capability that it cannot reach the next scope, writes included; two signed-in users unable to act on each other's avatars or grants or read each other's memory or closed channels, on complete serialized results; human tokens with wrong audience, issuer, expiry, algorithm, kind or future `nbf`, and application-only tokens, refused; an avatar token at `/mcp-admin`, the page and the token endpoint refused; a replayed or mismatched callback refused; each revocation ending an open wait and feed with nothing new arriving; an expired or used device code refused with nothing created; a reused refresh token revoking the grant; `create_avatar` without the permission, from a child, past the count and after the parent's revocation refused, and the count raced; a second grant ending the first's wait; the human disabled at the provider ending grants within the recheck bound; the lag report carries no count; the break-it list of `agent-credentials-design.md` section 13. Gate: captured, sanitized claim fixtures from each supported provider's page and `/mcp-admin`; one login and refresh against a real provider; one native login of each client in roadmap 8.8. Both contract snapshots checked in kkt-pro. |

## 4. Step 2.2: personal swarms (roadmap step 4a)

| Part | What lands |
|---|---|
| **What** | Pro's swarm-facts table keyed by the core's swarm ID: owner, personal flag, active flag, org, name (unique per owner). A personal swarm per user, made at first sign-in, never named or listed to agents or users ("my avatars"); kkt-format never names it. Migration: the default swarm becomes the one user's personal swarm when the org has one user (always so in key mode), else the shared space owned by the first server admin with every user of the org having access. The consent and approval pages choose the swarm from the user's access; human channel creation names the swarm; admin `create_channel`'s `swarm` required when the org has several, another org's swarm `not_found`. "Fixed at approval for good" is pro's rule: the swarm handle is a capability type constructible only by pro's `allows`, never a core check. Every user sees every channel in their swarms, closed included; a user's web view composes across swarms from the core's single-swarm pages; the live feed merges per-swarm subscriptions. |
| **Needs** | 2.1. |
| **Verified by** | A two-user test that neither sees the other's channels, agents, events or waits, on complete serialized results; a device code approved by a user without access to the chosen swarm refused with nothing created; a step-2.1 database with one user and one with several each migrated as described; the core's two-swarm tests run against pro's assembly. |

## 5. Step 2.3: shared swarms and groups (roadmap step 4b)

| Part | What lands |
|---|---|
| **What** | Groups (one org, kept by org admins, grant nothing by themselves). Shared swarms created, shared with groups only, deactivated and reassigned on the web page only; agents and `/mcp-user` never create or share them. Migration shares the shared space with a group of every user who had access. Approval pages offer every swarm the user has access to. Access is the union of current grants, never the one being changed; the cascade runs only on a true loss. The transition table of roadmap section 4 live: group removal; group deleted or swarm unshared; swarm deactivated (avatars deactivated, channels kept for humans with access and org admins; personal swarms never); user removed (refused while owning an active shared swarm; the personal swarm left inert, grants and pending approvals revoked, disabled row kept; refused for the last org admin unless the server admin does it); roles changed (no effect); owner changed (active shared swarm, active same-org owner, new name on collision, personal never); access lost any way (pending approvals refused, avatars deactivated, children revoked); org suspended (sign-ins and avatar tokens refused, waits end, nothing deleted). The cascade walks pro's grants and calls the core's `deactivate` and `end_waits` per swarm. Swarm and group pages; org admin tools for groups. |
| **Needs** | 2.2. |
| **Verified by** | Each row of the transition table, with a user removed during an open stream, during a wait, and concurrently with a write; loss of the last grant and retention of another grant as separate cases; a reassignment that collides with the new owner's swarm name, and one to a user of another org, refused. |

## 6. Step 2.4: orgs (roadmap step 5)

| Part | What lands |
|---|---|
| **What** | Several orgs on one server, one authorization server per server. Admission by claim binding (server admin only: Entra `tid`, Okta issuer, WorkOS `org_id`; a value binds to one org) and by invitation (org admin; email matched once; the provider must attest it verified, never on Entra). Every request matches the token's org claim to the stored org; a mismatch is refused and the user is not moved; a token without an org claim only for invited users; a token matching a binding and an invitation in different orgs refused. Removed users leave a disabled row. The store refuses any relationship write that crosses an org, in the transaction. Lanes under the core's org, with today's lanes, retired lanes and pinned versions in the default org; `kkt-lane-files` unchanged. Org announcement tools under new names; the server announcement tools keep their meaning and need the server role in login mode. `kkt lanes` and `kkt agent revoke` take `--org`, defaulting to the only org. Server admin pages: orgs (create, suspend, first admin, claim binding), server roles, server-wide login settings and limits. Org admins cannot bind claims or grant the server role. |
| **Needs** | 2.0 (the org), 2.3. |
| **Verified by** | Equal handles and equal lane names in two orgs through memory, reclaim, ownership, waits and administration; a token admitted by claim, by invitation, and refused by neither; a known subject presenting a token for another org refused and not moved; a removed user's token refused; a duplicate claim binding refused; an org admin unable to bind a claim, grant the server role, or reach another org, on writes as well as reads. |

## 7. Step 2.5: the user surface (roadmap step 6, optional, any time after 2.2)

| Part | What lands |
|---|---|
| **What** | `/mcp-user` in kkt-pro-mcp with its own tool text, instructions and contract snapshot, signed in as the user with no avatar token: list my swarms, my avatars and their grants; revoke a grant; deactivate; read their channels and memory; the user announcement (also set on the page). No approval here; never chats. This is the one hosted place a platform holds human power, by the human's deliberate choice. |
