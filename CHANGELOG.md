# Changelog

Release notes for each version of kkt, newest first. The release workflow
publishes a version's section as its GitHub release page, and refuses to
release a version with no section here. See "Preparing a release" in
[docs/releases.md](docs/releases.md#preparing-a-release).

Each section starts with a line `## X.Y.Z`, optionally followed by ` - ` and
a name. A named section's page starts with a line `# vX.Y.Z: name`; an
unnamed one's starts with its notes. A release candidate `vX.Y.Z-rc.N` uses
the section for `X.Y.Z`.

## Unreleased

### Fixes
- **Setup's web-key hint drops `--key-file` when a client becomes a server.** When `kkt setup` turned a machine whose record said it was a client into a server, the line telling you how to read the new web key named the file, as in `kkt key show --web --key-file '~/.config/kkt/web-key'`, though the key was in its default place. The hint now goes by the role setup is installing, not the record from before setup: a key in the default place reads `kkt key show --web`. A web key elsewhere is still named, and `kkt service install` run on its own still goes by the record as it is (#702).
- **A Docker `kkt upgrade` says where the server backs up the database before a schema upgrade.** Before it upgrades the database schema, the server saves a database-only backup of its own, in an `upgrade-backups` folder beside its database. As a service, `kkt upgrade` already said so; in Docker it said nothing, though the backup was made all the same. It now says that the backup goes in the data volume beside the database, under `/data/.local/share/kashkeshet/upgrade-backups` for the default database, and that the server's log gives the completed path: `docker compose logs kkt`, run in kkt's Docker folder, or the `log_file` the config file names (#701).

## 1.0.0

This release reorganizes kkt's code into crates that other programs can build on, and upgrades the database to a new storage layer that prepares for several swarms on one server. For an install it brings one new setup question, faster tool calls, and fixes to `kkt service` and `kkt upgrade`, most of them on macOS. Agents see no change: the tools, their text and their replies are as in 0.10.0. Read "What affects existing setups" before upgrading. A crate that depends on kkt's crates by git must also read "For crates that depend on kkt's crates by git".

### Setup
- **`kkt setup` can let the clients it sets up always use kkt.** After choosing clients, setup asks once whether they may always use kkt's tools and `kkt watch` without asking each time (`[y/N]`); `--allow-kkt` and `--no-allow-kkt` answer it. A yes adds, to each client's own settings, a rule for every tool of the MCP server named `kkt` and one for shell commands that start with `kkt watch`, and nothing for any other server or command: `mcp__kkt` and `Bash(kkt watch *)` in Claude Code's `settings.json`; `default_tools_approval_mode = "approve"` in Codex's `[mcp_servers.kkt]` and a `rules/kkt.rules` file; each kkt tool by name and `kkt watch *` in OpenCode's `opencode.json`; `mcp(kkt/*)` and `command(kkt watch)` in the Antigravity CLI's `settings.json`. Muse Code has no such setting, and setup says so. Files are merged and backed up as `kkt connect` does, and running setup again adds nothing twice. A rule you already have for kkt, such as a deny, is kept and named. If a client's settings can't be changed, setup says so and still finishes (#372).
- **Rewriting a client's JSON config keeps the order of its keys.** `kkt connect`, `kkt switch` and `kkt setup` used to write OpenCode, Antigravity and Muse Code configs back with every key sorted. That could reorder a person's own OpenCode `permission` rules, where the last matching rule wins. Keys now keep their places, and keys kkt adds follow them (#372).

### Fixes
- **`kkt uninstall` and `kkt switch` guide client recovery.** After removing a server, `kkt uninstall` names clients whose configured address still points there and prints a `kkt setup` command to move them. With no setup record, `kkt switch URL` checks the address first and prints the client setup command for that URL, key file and client selection; an invalid address or a key path that is not valid UTF-8 prints the error with no suggested command, and `kkt switch --local` says there is no recorded local server.
- **Status, setup and doctor confirm Docker container presence before offering adoption.** `kkt status`, `kkt setup` and `kkt doctor` check for a running or stopped Docker server container before treating a retained managed folder as an unrecorded install. A retained managed folder still gets the storage reuse notice during Docker setup. When Docker cannot answer, they explain which check failed.
- **On macOS, a service honours `log_file` from its config file.** A service installed or upgraded with this release reads `log_file` from its config at every start. With no configured path it uses the usual log under `~/Library/Logs/kashkeshet/`.
- **`kkt status` shows the local service's running version.** When the server answers, status prints its version; if the server cannot answer, status says the version could not be read and still shows the service details.
- **Quick MCP tool calls no longer wait about 40 ms each.** On a connection a client keeps open between calls, as agents' MCP clients do, every call after the first took about 40 ms longer than it needed. A tool's reply goes out as two writes, its headers and then its body. With Nagle's algorithm on, the second waited for the client to acknowledge the first, and clients delay that acknowledgment. The server now turns Nagle's algorithm off (`TCP_NODELAY`) on every connection it accepts: a call such as `whoami` takes about 0.3 ms instead of 42 ms. If the option cannot be set on a connection, the server says so in its log and still serves it (#407).
- **On macOS, `kkt upgrade` and `kkt service install` no longer fail while launchd is still removing the old service.** `launchctl bootout` returns before launchd has finished removing the service, and the `launchctl bootstrap` that followed at once could fail with `Bootstrap failed: 5: Input/output error` (`Operation already in progress` in launchd's log), leaving the new service installed but not loaded. Now, while `launchctl print` still finds the old service, a failed `bootstrap` is tried again every 250 ms, for up to 35 seconds (the service's 30-second stop timeout plus a margin); once the old service is gone, it is tried once more. A failure after that, or when the wait runs out, says that kashkeshet is stopped, that the new service is installed but not loaded, and that `kkt service start` loads it; from `kkt upgrade`, it adds that the upgrade is recorded only when `kkt upgrade` is run again (#369).
- **`kkt service install` no longer reports success for a server that cannot start.** When another program had the server's port, `install` said "Started kashkeshet", and the service manager then started the failing server again every 5 seconds, forever. Now `install` first checks that the server can listen on its address, and refuses, naming the address and the config file to change, before writing anything. After starting the service, it waits 3 seconds and checks that the server is still running; if not, it stops the service (on macOS, unloads it) and fails, pointing to `kkt service logs`. `kkt setup` installs the service the same way, so it fails at this step too, and offers to try again (#371).
- **On macOS, `kkt service` says plainly when you are not logged in at the desktop.** kkt's service runs in your desktop login session. Without one, as over SSH before anyone has logged in at the screen, `kkt service install` (with or without `--dry-run`), `start`, `stop`, `status` and `uninstall` now say so and suggest logging in at the desktop or running `kkt serve` yourself, in place of launchd's "Could not print domain: 125" error. An install refused this way writes no service file. `kkt serve`'s warning and `kkt doctor`'s service check say only that no one is logged in at the desktop, so the service cannot be asked.
- **`kkt setup` and `kkt switch` check a server's address as `kkt doctor` and `kkt connect` do.** They now refuse an address with a user name or password, a query, a fragment or a control character, before asking the server anything and before writing anything, as `kkt doctor` and `kkt connect` already did. Their refusal is now worded as the doctor's: "URL must be an absolute http:// or https:// address", "URL contains a control character", or "put credentials in the key file, not in the URL; query strings and fragments are not supported", in place of "\"<address>\" is not a server address: it starts with http:// or https://". Reading an existing setup record does not check its URL again (though switching back to that server with `kkt switch --local` does check it). Whether a bare address gains `/mcp` is as before for each command.
- **A lost connection to the server says why.** `kkt watch`, `kkt register` and `kkt reclaim` said only "MCP connection failed". They now add the cause in parentheses, such as "MCP connection failed (the server could not be reached)": timed out, an HTTP status, the connection closed, the session expired, or an answer that was not MCP. The cause comes from the kind of failure, never from the server's text.
- **One failure of `kkt setup` for kkt in Docker is worded differently.** If setup cannot make a key copy private after opening it, it now says "could not restrict <path>: …" where it said "could not write <path>: …". Setup fails at that point as before; only the words change. Every other way writing a key copy can end is the same as before, byte for byte and mode for mode.
- **Rewriting a client file no longer changes its mode.** `kkt setup`, `kkt connect` and `kkt switch` write a changed client file through a private temporary file, so an existing file such as Claude Code's `settings.json` (mode 644) came back mode 600 even though it holds no key. A changed file that was there now keeps the mode it had; a new file is still made private, and a file that holds a key still ends mode 600. The restore instructions now name the `-wal`/`-shm` files after the database file's own name and say that a restored database reuses message IDs, so a `kkt watch` state file past the backup's highest ID must be deleted (with `--after-id` naming that ID, if known) before the watch restarts. The download check in the release notes drops the checksum file's blank line before checking, so macOS no longer prints a warning beside OK.
- **`kkt upgrade` for kkt in Docker now prints where its backup went.** After backing up the container before upgrading, it prints `Backed up to <path>`, matching a service upgrade.
- **CLI errors print plainly on standard error, and status and key hints are clearer.** Command refusals and errors (such as `kkt upgrade` on a client, `kkt backup`, `kkt lanes`, `kkt setup`, and `kkt serve` before its log starts) now print `error: …` on standard error instead of a timestamped `ERROR` log line; `kkt serve` keeps logging as before once its log has started. `kkt key show --web` gives a plain message when the web key is missing, and `kkt service install` prints bare `kkt key show --web` when ordinary key lookup resolves the newly written key (from the setup record when one exists, or from the configured or default access key otherwise), adding `--key-file <path>` when it does not. `kkt status` prints `Mode:` and `Server:` before `Web key:` and `Admin key:`, says "Client only; no server is managed on this machine." for a client, and prints `Settings file: present` / `missing` in Docker status. The installer's last line now makes clear that `kkt upgrade` is for upgrading a server running here.
- **Explicit `--db` or `--config` works on a client machine.** `kkt backup` and `kkt lanes` (`import` and `export`) now accept an explicit local `--db` or `--config` even when the setup record says client. With neither flag, they still direct you to the server machine. On a client machine, `kkt backup DIR --db X` without `--config` backs up only the database and says so, rather than copying unrelated default `config.toml` or key files; with `--config`, it copies that config and only the keys it names.
- **`kkt switch` reports each client's own previous address and names only moved clients.** Instead of printing `(before: …)` from the setup record on the summary line, `kkt switch` reads each client's config before updating it and prints `(before: <url>)` on that client's `Configured:` line when the previous address is present and passes the server-address check (omitting it otherwise, while leaving key-permissions lines intact). Repeated client names in `--clients` are treated as one. When only a subset of connected clients is switched (e.g. `--clients codex,opencode`), the closing line names only the clients that moved (`Codex and OpenCode now use …`); when all connected clients move, it stays `This machine's clients now use …`; and when automatic discovery finds no connected clients (no `--clients` flag) or `--clients none` leaves no clients selected, it names only the CLI commands that changed server.
- **Setup no-terminal and EOF errors, fresh service web-key output, and client `.bak` deduplication.** Missing-flag errors without a terminal and terminal end-of-input errors now read plainly (e.g. `error: no terminal to ask for the server's MCP address; pass --url` and `error: no answer when asked for the server's MCP address; pass --url`). Fresh `kkt setup --mode service` prints the web-key line once, using the same `kkt key show --web` lookup rule. Rewriting a client settings file skips creating a new `.bak` when any existing regular, independent `.bak` or `.bak.N` of that file (even past a gap) already has identical content; whenever independence cannot be established (such as a symlink, a hard link to the file being rewritten, unreadable original metadata, or on non-Unix platforms), a fresh exclusive backup is created.
- **Docker setup says when it will reuse existing storage.** Before changing anything, `kkt setup` for Docker tells you if it will reuse an existing managed folder or data volume, names both, and continues without asking a question.
- **Backups are private from creation, record the highest message ID, and surface pre-migration copies.** On Unix, every file kkt writes into a backup folder starts at mode 0600, including the SQLite database, `config.toml`, `admin-key.name` and `about.txt`. `kkt backup` (for a service, with no setup record, on a client with `--db` or `--config`, and inside Docker, whose backup runs the same command in the container), service upgrade backups (even when the copied database is at an older schema), and the server's pre-migration database backup all read the highest message ID read-only from the finished copy—never opening or changing the source database—so a restore can pass it to `kkt watch --after-id`. Once the copy finishes (a lock that blocks reads still fails the backup as before), there are three outcomes: a readable database with messages records `highest message ID: N` in `about.txt`; a valid database with zero messages omits the line with no warning; and a copy whose message IDs cannot be read or whose `about.txt` cannot be updated still succeeds as a backup and omits the line—CLI backups (`kkt backup`, service upgrades, and Docker backups forwarding the line to the host) print the reason in one plain line, while a server's pre-migration backup runs that check in the background and logs a `WARN` to the server log. Service upgrades also report the newly completed pre-migration database backup as well as the full backup made before restart (or name its directory if still in progress). Older backups (or an older Docker image writing an upgrade backup) may lack the `highest message ID` line; they restore as before, and when the line is absent see [restoring a backup](docs/backup.md#restoring) for the watch fallback.
- **Exit codes are now stated and pinned.** Wrong usage of any kkt program (a flag or value its parser cannot read, a `--clients` name it does not know, or a missing subcommand) exits 2; `kkt agent` with no subcommand prints its help and exits 2; every other failure exits 1. `kkt-keymode` and `kkt-fake-product`, which read their arguments themselves, now also exit 2 for wrong usage instead of 1, and read their path arguments in their native bytes, so a path that is not valid UTF-8 is used as a path rather than crashing. This is stated in [Setup](docs/setup.md), and a test in each program pins both codes.
- **`kkt lanes export` ends with the same line in every mode.** It now always prints `Exported N lanes to DIR`; an export through Docker used to print `Exported to DIR` with no count, and now counts the lanes its in-container export listed.

### Under the hood
- **kkt is a workspace of crates that other programs can build on.** The 27 crates of 0.10.0 are now 63, each one kind: a contract (traits and plain values), logic, an effect on the machine, or the assembly that wires them. Every dependency is injected, and every error is a type of its own in place of text, apart from 21 recorded exceptions, which `CLAUDE.md` lists and CI checks. `CLAUDE.md` lists each crate and what it owns, and `docs/architecture/` holds an interactive map of them. Two development programs check that the shared crates stand alone: `kkt-keymode` assembles key mode again with none of the `kkt` program's code, and `kkt-fake-product` assembles them with two swarms and checks that nothing of one appears in the other.
- **For people building from source:** `cargo install --path . --locked` still builds and installs `kkt`. The web page preview now runs with `cargo run -p kkt-webapp-preview`. New tests pin each command's error line and exit code (`tests/error_lines.rs`), what a 0.10.0 database answers after its upgrade (`tests/migrations/v0_10_0.rs`), and the records and notes kkt 0.10.0's setup wrote (`crates/kkt-setup/tests/v0_10_0`).

### What affects existing setups
- **The database is upgraded.** The first start rebuilds the database's tables through kkt's new storage layer, which describes tables, migrations and search for any database and no longer uses SQLite's own word splitting or migration count. Every row is kept, and nothing an agent, the web page or the CLI sees changes, search results and excerpts included. The upgrade also adds a `swarms` table holding one swarm, `sw_main`, and a `swarm` column on `agents` and `channels` that puts every avatar and channel in it: every lookup of an avatar or channel is now bound to that swarm, which prepares for several swarms on one server. The two handoff-note columns of `agents`, whose notes an earlier release copied into memory entries and which nothing has read since, are dropped. On a database with a million messages the rebuild takes a few seconds. Before upgrading, the server backs up the database into `upgrade-backups` beside it, and refuses to start if it cannot (see `docs/backup.md`). To go back to 0.10.0, put back that backup as `docs/backup.md` and `docs/docker.md` describe; messages and changes made after the upgrade are then lost.
- **A database from before 0.10.0 is no longer upgraded directly.** Opening one stops with "this database is from a kkt version older than 0.10.0; upgrade it with kkt 0.10 first, then with this version", and leaves it unchanged. Run kkt 0.10 on it once, then this version.
- **`kkt upgrade` upgrades a 0.10.0 install** as it did before, for a service and for kkt in Docker: it backs the server up first (the service's database and keys, or the container's backup), installs the new version, and records it only after that succeeds. On macOS a service upgrade now waits, if it must, while launchd removes the old service, and says what to do if the new one still does not load (see Fixes).
- **The setup record, the note of an unfinished setup, the managed Docker folder, keys and key files, and the config file and its settings are unchanged.** kkt reads the setup records and notes 0.10.0 wrote, and writes them back the same, byte for byte. The Dockerfile, Compose files, `tailscale/serve.json` and the systemd unit template are unchanged since 0.10.0. The launchd plist now supplies a fallback log path. Key file names, places and modes, and backup folders and names, are as before (see Fixes for `about.txt`, backup file modes, and client `--db` backups).
- **Agents see no change.** The tools, their parameters and descriptions, error codes, replies and the built-in instructions are as in 0.10.0, so the instructions hash each server run records (`instructions_sha256`) is unchanged for a server with the built-in text, and so are the run's recorded settings. Agents connected before the upgrade need not reconnect. Clients and servers of 0.10.0 and this release work together: `kkt watch`, `kkt register`, `kkt reclaim` and `kkt connect` call the same tools with the same parameters and read the same fields.
- **The CLI gains two setup flags, and some messages and exit codes change.** `kkt setup` gains `--allow-kkt` and `--no-allow-kkt` (and `kkt serve` gains the hidden `--default-log-file` flag used by the macOS launchd plist); every other user-facing command and flag is as before. `kkt service install`, and so `kkt setup` for a service, waits 3 seconds after starting the service to check it is still running. Apart from the CLI error-format, exit-code, and command-message changes listed under Fixes, every other message and exit code is as before.
- **JSON client configs keep their key order.** The next `kkt connect`, `kkt switch` or `kkt setup` that changes an OpenCode, Antigravity or Muse Code config leaves its keys in their order instead of sorting them. A file an older kkt already sorted stays sorted. The settings in it are the same either way.
- **Setup changes client permissions only when asked.** Enter, `--no-allow-kkt`, and a run with no terminal and no flag change nothing, so scripted setups run as before. A yes writes files kkt did not write before (Claude Code's `settings.json`, Codex's `rules/kkt.rules`, the Antigravity CLI's `settings.json`), merging into any that exist and backing them up first.
- **Docker image**: `ghcr.io/sam-mfb/kashkeshet:1.0.0`.

### For crates that depend on kkt's crates by git
The shared crates are reorganized so that every dependency is injected and each crate is one kind: a contract (traits and plain values), logic, an effect on the machine, or the assembly. A crate such as kkt-pro that depends on them by git must follow these changes. Each item below gives where a thing is now. Nothing an agent, a person or an install sees changes, apart from what the sections above list.

#### Crates
- **The crates of 0.10.0.** `kkt-client-config` is now `kkt-llm-agent-config`, and Claude Code's own command is `kkt-llm-agent-command`. `kkt-config` is removed: each of its items is now a constant, or a field of the `Settings` of the crate that uses it. `kkt-events` is a private module of kkt-rules. `kkt-format` is kkt-mcp's module `kkt_mcp::result_format`. `kkt-logs` is split into `kkt-log-tracing` and `kkt-rolling-file`. `kkt-service` is `kkt-bare-service`, with `kkt-bare-service-launchd` and `kkt-bare-service-systemd`. `kkt-settings` is removed: each program gathers its own settings, and the config file's format is `kkt-config-file`'s. `kkt-store` is merged into kkt-rules, and its store is private. Every other crate of 0.10.0 keeps its name; many of their items moved to the new crates below. Rename the dependencies and paths.
- **Names that existed only between releases.** A crate that followed `next` or `refactor` by git may name crates that never shipped. Each is now: `kkt-operate`, `kkt-install-commands` and `kkt-operator-commands`; `kkt-server-listen`, `kkt-listen`; `kkt-mcp-formatter`, `kkt_mcp::result_format`; `kkt-server-keys` and `kkt-admission-os`, `kkt-keys` and `kkt-keys-os`; `kkt-terminal-os`, `kkt-terminal`; `kkt-agent-files-os`, `kkt-agent-files`; `kkt-web-preview`, the dev-only program `kkt-webapp-preview`; `kkt-lane-commit`, `kkt-revision`; `kkt-client-command`, `kkt-llm-agent-command`; `kkt-service-launchd` and `kkt-service-systemd`, `kkt-bare-service-launchd` and `kkt-bare-service-systemd`; `kkt-service-os`, `kkt_listen::try_bind`; `kkt-container-os`, gone (`kkt_containerized_service::Containerized` over `kkt_container_docker::Docker`); `kkt-remote-access-os`, `kkt-remote-access-tailscale`; `kkt-diagnostics-os`, `kkt-probe`; `kkt-logs-os`, `kkt-rolling-file`; and `kkt-lane-files-os`, `kkt-client-config-os`, `kkt-config-file-os` and `kkt-setup-os`, `kkt-files` with the program's adapters. A name of the form `x-something` means the crate implements `x`'s contract.
- **New contract crates.** `kkt-api-agent` (`Api` and its areas, and the records every level shares, including `SwarmId`, `Actor`, `Operator`, `Audit`, `RuleError` and `Code`, which were kkt-rules'), `kkt-api-operator` (`OperatorApi`, with `Views`, `Changes`, `Lanes` and `Server`) and `kkt-api-admin` (`AdminApi`), all implemented by `kkt_rules::Rules`; `kkt-entropy` (`Entropy` and its stand-ins, from kkt-names); `kkt-log` (`Log`, the structured log that kkt-mcp, kkt-web and kkt-server take in place of `tracing`); `kkt-machine` (`Env` and `Platform` as plain values, and `Machine`, see below); and `kkt-identity` (`Identify`). `kkt-clock` keeps `Clock` and the time types, and `SystemClock` moves to `kkt-clock-system`.
- **New logic crates.** `kkt-hash` (`sha256`), `kkt-search` (search's words, terms and excerpts, from kkt-db), `kkt-identity-keymode` (`KeyMode`, from kkt-identity), `kkt-config-file` (the config file's format, from kkt-settings), `kkt-toml` and `kkt-deployment` (below). `kkt-api-sim` is new test support: the simulated application, for tests and the page preview, behind `testing`.
- **Effect crates.** What touches the machine is in a crate of its own, which the program adapts to the logic's contract: `kkt-entropy-os` (`OsEntropy`), `kkt-machine-os` (`OsMachine`), `kkt-shutdown-os` (`StopSignals`, from kkt-shutdown, which keeps `Shutdown`), `kkt-backup-os` (`OsBackups`, below), `kkt-keys-os` (`OsKeyFiles`), `kkt-files` (`Files`), `kkt-listen`, `kkt-rolling-file`, `kkt-terminal`, `kkt-agent-files`, `kkt-browser`, `kkt-revision`, `kkt-probe`, `kkt-llm-agent-command`, `kkt-clock-system`, `kkt-db-sqlite`, `kkt-container-docker`, `kkt-remote-access-tailscale`, `kkt-bare-service-launchd` and `kkt-bare-service-systemd`.
- **No `real` feature.** No crate has a `real` feature: each effect crate builds all of its code. **This breaks a crate that depends on kkt by git and asks for `real`**: Cargo refuses a dependency with a feature it does not have. Drop `features = ["real"]` from every kkt crate in your `Cargo.toml` on the same update. An effect crate's third-party libraries are ordinary dependencies of it.
- **The install's commands and the operator's commands.** `kkt-install-commands` has the commands that install and look after kkt: `setup`, `lifecycle`, `service`, `doctor`, `record`, `keys` and `deployment`, over `InstallParts`, with `Config`, `ServeFacts`, `ServiceInputs`, `CheckService`, `CheckedService`, `ServiceDefaults`, `SetupFiles`, `ConfigText`, `Databases` (including `highest_message_id`), `ImportLanes` (setup's lane check and import) and `Output`. `kkt-operator-commands` has `key`, `agent` and `lanes`, and the key finders in `keys` (`selected_key_path`, `optional_key_path`, `local_operator_key`), over `OperatorParts`: `installed`, `serve` (its own `ServeConfig`), `paths` (`Paths`), `key_files`, `entropy`, `lane_servers`, `lanes`, `lane_commit`, `database` (its own `Databases`, with `open`), `clock` and `output`. `credential_file_check` and `CredentialFileFix` are kkt-agent-commands'. The program's `machine::operate` is `machine::native`, and its `NativeOperate` is `NativeParts`; `HereLanes` and `SetupLanes` keep their names.
- **`kkt-clock` takes tokio only for `testing`.** Its `FixedClock` is the one user, so a release build of kkt-clock has no tokio.
- **Items only their own crate uses are no longer public.** kkt-keys' `ACCESS_KEY_FILE_NAME`, `WEB_KEY_FILE_NAME`, `ADMIN_KEY_FILE_NAME` and `ADMIN_NAME_FILE_SUFFIX` (the path functions place the files); kkt-names' `ADMIN_PREFIX` and `CHANNEL_PREFIX`; kkt-lane-files' `EXTENSION`; kkt-diagnostics' `KEY_CHECK` and `SERVER_CHECK`; kkt-config-file's `CONFIG_DIR` and `CONFIG_FILE_NAME` (`config_dir` and `config_file` give the paths); kkt-rolling-file's `RotatingFile::open` (`open_log_file` opens one, after checking its policy); kkt-admission's `Mode`, `Open` and `AnyBearer` (an `Admission` names its mode); kkt-agent-files' `read_secret` and `FileLock`; and kkt-agent-client-mcp's `AdminRemote` (`Mcp` gives the admin's view as a `Watched`).

#### Contracts and their implementations
- **Containers.** kkt-container's command-level `Host` and free functions give way to two layers. `kkt-container` holds only `Projects` (a Compose project, as a contract for any program), its records, `Folder` (without `backups`) and `testing::MemoryProjects`, and depends on no other crate of the workspace; its `ServiceConfig::working_dir` is an `Option<String>`, `None` when the image names no folder. `kkt_container_docker::Docker` implements `Projects` with Docker Compose, and `Docker::new` takes no browser. Both are platform crates. `kkt_containerized_service::ServiceContainer` is kkt's server installed in a container, with its records (`Inputs`, `Sharing`, `KeyCopies`, `Provisioned`, `State`, `Login`, `Existing`, `KeyCopy`, `InServer`, `Arg`, `Carry`), `ConfigReader` with `ContainerConfig`, `LoginLink` and `testing::Memory`; `kkt_containerized_service::Containerized` implements it over `Projects`. Its methods return `ContainerError`, an enum of the kinds of failure, in place of `String`; each kind's text is the same as before, and `String::from` gives it. It has no lane operations, and `LanesImport` goes: `run_in_server` runs the server's own program in the installed container as an `InServer` says (its arguments, `Arg::Text` or `Arg::Folder` for the work folder; the work folder's prefix; and `Carry::In` files or `Carry::Out` a folder), and `config_home_file` reads a file under the container's config home. `provision`, `add_admin_key` and `upgrade` take a `KeyCopies` (the access, web and admin key copies' paths), which `kkt_deployment::docker_key_copies` gives; `add_admin_key` takes the admin name as text, and `status` takes the config file's path under the container's config home (`kkt_config_file::config_file_in_home`). `WEB_KEY_FILE_NAME`, `ADMIN_KEY_FILE_NAME` and `NO_ADMIN_KEY_EXIT` are kkt-keys', the first two as `WEB_KEY_COPY_FILE_NAME` and `ADMIN_KEY_COPY_FILE_NAME`. `Projects` gains required methods `has_volume(project, name)` (and `testing::MemoryProjects` gains `with_volume`) and `has_container(project, service)`, and `ServiceContainer` gains required methods `reuses_data(folder, volume)` and `server_present(folder)`; every implementation of `Projects` or `ServiceContainer` must add the new methods. Compose files and settings files are unchanged (see Fixes for Docker status, setup, backup and upgrade behavior).
- **Remote sharing.** `kkt_remote_access::RemoteAccess` replaces its command-level `Host` and free functions, and `kkt_remote_access_tailscale::Tailscale` implements it; the program injects it directly. `kkt-remote-access` holds the contract and `testing::Memory`, with no third-party dependency. Files, commands and messages are unchanged.
- **The service manager.** `kkt_bare_service::Service` replaces `Manager`, `System`, `DryRun`, `Command` and `Finished`: what kkt asks of the service manager, in kkt's terms, with `Unsupported` for other systems (made with `Unsupported::new`, given the text to say, which `ServiceError::Unsupported` carries) and `testing::Memory` for tests. `kkt_bare_service_launchd::Launchd` and `kkt_bare_service_systemd::Systemd` implement it directly, each holding its own manager's files and commands; the program picks one by platform and injects it into `InstallParts::service`. launchd's waits (`removal_wait`, `reload_retry`) are `kkt_bare_service_launchd::Settings`, given to `Launchd::new`, and `ServiceError::ReloadFailed` holds the text launchd's wrapper words. `ServiceError` gains `NoLoginSession { refusal, fact }` (the user has no login session for the service to run in; the implementation words both texts, `refusal` for a refused service command and `fact` for the fact alone, and kkt-bare-service-launchd returns it when launchd has no `gui/<uid>` domain for the user) and `LogConfig(Box<dyn Error + Send + Sync>)` (reading the service's configured log path failed). A `match` on `ServiceError` needs both new arms. `Launchd` gains `with_configured_log` to read `log_file` from the service's config file. `kkt_install_commands::service::run` takes no `Env`. What an installed service runs is kkt-deployment's (below). The `kkt service` command, the launchd label and the systemd unit file are unchanged; on macOS, the launchd plist now passes `--default-log-file` instead of `--log-file` so a configured `log_file` wins, and `kkt service install` names `--key-file` in its web-key hint when bare `kkt key show --web` would not read the file just written (see Fixes).
- **A client's own command.** `ClientCommand` is kkt-llm-agent-config's (`kkt_llm_agent_config::ClientCommand`: remove kkt's server, add it as the client's own entry), with its stand-in `testing::Recorder` and `Call` behind kkt-llm-agent-config's `testing` feature. `configure` takes a `&dyn ClientCommand` after the host, `Client` gains `configured_url(self, env, host)`, and `kkt_llm_agent_config::Host` loses `claude` and gains `mode`, `set_mode`, `list_dir` and `read_independent_file`, which every implementation of `Host` must now give. kkt-llm-agent-command declares no contract: `kkt_llm_agent_command::Claude`, made with `Claude::new(server_name, retry)` (kkt's are `"kkt"` and `"--write"`), has `remove_server` and `add_server` as its own methods, and a program adapts it to `ClientCommand`. The commands run and every message are unchanged.
- **Probing a server.** `Prober`, `Probing`, `KeyFile` and `Check` are kkt-diagnostics' (`kkt_diagnostics::Prober` and so on), with the stand-in `kkt_diagnostics::testing::Memory`. `Prober` has `key_file`, `answer` and `initialize`, with kkt-diagnostics' own copies of the records, and `Probing` names what it yields. `kkt-probe` probes any MCP server and words nothing for kkt: `kkt_probe::HttpProber::answer(url)` makes the plain GET and `initialize(url, key)` the MCP `initialize`, each returning plain facts (`Answered`, `Initialized`, `Status`, `Reply`, `ReplyError`, or `Unprobed` when no request can be made); its `Settings` has `client_name` and `client_version`, and no `server_check` or `key_check`. A program adapts it to `Prober`. `kkt_keys::KeyFiles` gains `mode`, a file's permission bits, which the program uses for the doctor's key-file check. Every probe check's name and wording are unchanged; `kkt doctor` shares the unrecorded-Docker check (see Fixes).
- **A lane folder's commit.** `LaneCommit` is kkt-lane-files' (`kkt_lane_files::LaneCommit`), with its stand-in `kkt_lane_files::testing::Memory` behind kkt-lane-files' `testing` feature. kkt-lane-files' `git` module (`Git`, `Ran`, `commit`) is gone, `kkt_lane_files::Disk` loses `git_commit`, and `read_folder` takes the `LaneCommit` beside the `Disk`. `kkt_revision::Git` has `commit` as its own method, with git's meaning, and a program adapts it to `LaneCommit`. The commits recorded and every message are unchanged.
- **Opening a link in the browser.** `Browser` is kkt-containerized-service's (`kkt_containerized_service::Browser`). `kkt_browser::SystemBrowser` opens a link with `open` or `xdg-open` and has `open` and `open_failure` as its own methods; a program adapts it to `Browser`. `kkt_containerized_service::LoginLink` and kkt-terminal's `BrowserLink` keep only `show` and `open_requested`, and `BrowserLink::new` takes the words that come before the link. The opener and every message are unchanged.
- **Agent clients.** `kkt-agent-client` is the contract for a client of kkt's server: `Servers`, `Avatars` and `Watched`, with `Address`, its records, `Failure` and `testing::Memory`. `Watched` has `polls`: whether `wait` answers at once instead of waiting on the server. The implementation over MCP (`Mcp`, `Client`, `Remote`, `Http`, `HttpReply`) is `kkt-agent-client-mcp`, with `Settings`; the admin view (`Servers::admin`, which takes no clock) answers at once, and kkt-watch asks it again every `Settings::watch_poll` (2 seconds) until something comes or the wait is over. kkt-agent-client-mcp's `Settings::watch_admin_poll` goes. kkt-watch's `Server`, `Channel`, `Message`, `Waited`, `NewerLane` and `Failure`, and kkt-agent-commands' `Servers`, `Avatars`, `Address`, `Registered`, `Reclaimed` and `Failure`, give way to the contract's. The credential and watch-state files are `kkt-agent-files`'. Messages and files, and how `kkt watch --admin` behaves, are unchanged.
- **The machine's facts and the stop signals.** `kkt_machine::Machine` declares `env`, `platform`, `process_id`, `program_path`, `path_dirs` and `current_dir`, with a stand-in `kkt_machine::testing::FixedMachine`; call them on `kkt_machine_os::OsMachine` with `Machine` in scope. `Env`'s `claude_config_dir` and `codex_home` are gone: `Env::named` holds the folders the program asks for by variable, `Machine::env(names)` takes them, and kkt-llm-agent-config's `ENV_FOLDERS` are the two it needs. `Env` gains `data_home()`, the XDG data home (`$XDG_DATA_HOME`, or `~/.local/share`). `kkt_shutdown::Signals` declares `stop_on_signal`, which kkt-shutdown-os' `StopSignals` implements; it returns `kkt_shutdown::Signal` (`Interrupt` or `Terminate`) in place of a `&'static str`, whose `Display` gives the same words as before (`Ctrl-C`, `SIGTERM`), and kkt-shutdown has a stand-in, `testing::OnCue`. `Shutdown` and `StopSignals::listen` are unchanged.
- **File access.** `kkt_files::Files` is one set of methods for files on this machine: `read`, `write`, `file_names`, `dir_entries`, `read_independent_file`, `create_dir_all`, `rename`, `remove_file`, `exists`, `create_private`, `restrict`, `mode`, `set_mode`, `absolute`, `canonicalize`, `read_if_present`, `write_by_rename` (the same `<name>.partial`, then a rename), `remove_if_present` and `is_file`. The config file's reads and writes are kkt-config-file's, over a `Disk` it declares (read, exists, make folders, write) that a program adapts `Files` to: `kkt_config_file::files::{read, read_default, read_named, read_instructions, write, ReadError, WriteError}`, each taking the `&dyn Disk` first. Setup's record and unfinished note are read and written by the program over `Files`; kkt-setup's `parse` and `render` are unchanged. What setup asked of the machine is `Files`' `create_dir_all`, `absolute` and `canonicalize`, `Machine`'s `program_path` and `path_dirs`, and the program's own `kkt_path` and check of `$PATH`. `try_bind` is `kkt_listen::try_bind`. Apart from the file-mode and backup changes listed under Fixes, everything on disk is unchanged.
- **TOML.** `kkt-toml` is the only crate that uses the `toml` and `toml_edit` libraries. It parses TOML text into its own tree of values (`parse`, `Table`, `Value`), reads and writes typed records (`read`, `write`), and edits a document while keeping its comments (`Document`), with errors of its own (`ParseError`, `Place`, `WriteError`, `EditError`). kkt-config-file, kkt-llm-agent-config, kkt-setup and kkt-mcp's build script use it, and no longer depend on `toml` or `toml_edit`. Their public items, and every message they give, are unchanged.
- **Logs.** The log file is `kkt-rolling-file`: `RotatingFile`, with `open_log_file(path, policy, clock)`, which checks the policy and opens the file, and `LogPolicy` with its `DEFAULT`; it returns `OpenError` (`Policy` with a `PolicyProblem { value: PolicyValue, rule }`, or `File { path, error }`) in place of a message, which the caller words. kkt-logs' plans (`should_roll`, `prune_due`, `rotation`, `pruning`, `Rotation`, `Pruning`) and `LogPolicy::check` are private to kkt-rolling-file. `TracingLog`, `init_logging`, `init_stderr_logging` and `logging_started` are `kkt-log-tracing`'s. `init_logging(writer, own_targets, own, dependencies)` takes the writer to log to (`None` for stdout) and the targets of the program's own code (kkt's are `["kashkeshet", "kkt"]`), and `init_stderr_logging(own_targets, own)` the same targets. kkt-log's `Level` is the one level type, with `Level::ALL` and `Level::name`; kkt-log-tracing's `parse_level` reads a setting into it, and `DEFAULT_LOG_LEVEL` and `DEFAULT_DEPENDENCY_LOG_LEVEL` are `Level`s. `LogLevel` and `check_dependency_log_level` are gone: the dependency level's rule is the `kkt` program's. The `kkt` program logs through kkt-log's `Log` and no longer depends on `tracing`. Every log line and message is unchanged.
- **The server's keys.** The server's keys are `kkt-keys`, and their files on disk `kkt-keys-os`. kkt-admission depends on kkt-keys, never the reverse, and keeps who is let in: `Admission`, `AdminAdmission`, `SharedKey`, `BearerToken`, `Credentials`, `Decision`, `Principal`, `ServerKey`, `Refusal`, `WebAdmission`, `WebSession`, `key_refusal`, and `server_keys::{check, KeyTexts, ServerKeys, KeyRefusal}`, at the same paths. Moved, with their old paths:
  - `kkt_admission::{AccessKey, SettingError, check_access_key, ACCESS_KEY_FILE_MODE, access_key_file, web_key_path, admin_key_path, admin_name_path}` and `kkt_admission::server_keys::{KeyText, bound_to, bound_in}` are now `kkt_keys::` items of the same names;
  - `admin_name_line` and `admin_name_written` are kkt-deployment's (below);
  - `kkt_admission::SharedKey::generate(entropy)` is gone: draw a new key with kkt-entropy's `entropy.random_chars(kkt_keys::NEW_KEY_ALPHABET, kkt_keys::NEW_KEY_CHARS)`, which makes the same keys;
  - `kkt_admission::testing::MIN_ACCESS_KEY_BYTES` is now `kkt_keys::testing::MIN_ACCESS_KEY_BYTES`, and kkt-admission has no `testing` feature;
  - the key files are a contract, `kkt_keys::KeyFiles`, which `kkt_keys_os::OsKeyFiles` implements on disk; `kkt_keys::testing::Memory` is its stand-in. `ReadError` is `kkt_keys::ReadError`. `KeyFiles::new(access, web, admin)` and its `access`, `web`, `admin` and `admin_names` are now the plain value `kkt_keys::SelectedKeys { access, web, admin }` and the trait's `read_access`, `read_web`, `read_admin` and `read_admin_names`; `KeyFiles::read` that names its file is `read_key`. `make_default_key(access, generate)`, `new_key_file(path, force, generate)` and the key writers are the trait's `make_default_key`, `new_key`, `write_key` and `write_admin_name`, the generator now a `&mut dyn FnMut() -> String`. `KeyFiles` loses `exists`: `try_exists` says whether a file is there or why that cannot be told, and `make_default_key` refuses a key file it cannot look at, where it made a new one;
  - `InstallParts::key_files` and `OperatorParts::key_files` take `&dyn kkt_keys::KeyFiles`, beside `entropy`, which new keys are drawn from.

  Key checks, refusals, file names, file modes and how keys are written, read and hashed are unchanged.
- **Backups.** `kkt-backup-os`' `OsBackups` implements kkt-backup's `Backups` contract (`write`, `record_highest`, `finished` and `prune`), creating every copied file and `about.txt` privately (mode `0600` on Unix) and taking a database copier that creates its destination privately and exclusively; kkt-backup keeps the layouts (with `FileCopy::private = true`), makes `ABOUT_FILE` public, adds `highest_line`, and has `testing::Memory`, and `InstallParts::backups` takes `&dyn kkt_backup::Backups`. `kashkeshet::machine::database::highest_message_id(path)` (returning `Result<Option<i64>, HighestError>`) opens a finished backup copy via `SqlitePlace::open_snapshot` to read its highest message ID without migrating or creating journal files; it uses `block_in_place` and `Handle::current()`, so callers must invoke it on a finished copy inside a multithread Tokio runtime (calling it outside Tokio or on a current-thread runtime panics on a readable copy). Backup folders and names are unchanged (see Fixes for `about.txt`, backup file modes, and client `--db` backups).
- **Platform crates say nothing of kkt.** kkt's words are their caller's: kkt-log-tracing's targets (above); kkt-rolling-file's refusals (above); kkt-remote-access-tailscale's `Tailscale::new(rerun)` replaces the unit `Tailscale` (kkt's is `` "`kkt setup`" ``); kkt-entropy's `testing::SameHandleEntropy` is `testing::FirstOfLongListsEntropy`, unchanged. Every message a person sees is unchanged.

#### What kkt-setup held
kkt-setup is now the setup record and the conversation that produces it: `kkt setup`, `kkt switch`, and adopting a server installed with no record. `kkt_setup::Steps` gains required method `docker_data_notice(&self) -> Option<String>`, and `kkt_setup::SwitchSteps` gains required methods `client_url(&self, client: Client) -> Result<Option<String>, StepError>` and `validate_address(&self, url: &str) -> Result<(), StepError>`; every implementation must add them. Its other parts moved to the crates that own their subjects. Paths and file names are unchanged (see Fixes for setup, status, uninstall and switch output changes).
- **What follows from how kkt is deployed is kkt-deployment's.** `kkt_deployment::data_dir`, `default_db`, `docker_folder` and `docker_url`; `guard`; `status`, `status_looks_for_unrecorded`, `Status` and `StatusThen`; `running_version`, `upgrade_plan`, `upgrade`, `RunningVersion`, `UpgradePlan`, `Replace` and `Upgrade`. They take facts the crate declares (`Deployment`, `RecordedDeployment`, `ServerVersion`, `UnrecordedDeployment`, `DeploymentEndpoint`) in place of kkt-setup's `Record`, `Unfinished` and `Unrecorded`, and kkt-install-commands reads the record into them (`kkt_install_commands::deployment`). `UpgradePlan` no longer carries the record: once the server is replaced, the caller records the target version. kkt-setup's `unfinished_mode` is `kkt_install_commands::record::unfinished_mode`, and kkt-setup gains `version_not_known`.
- **How a client reaches the server is kkt-deployment's.** kkt-setup's `connection` module is `kkt_deployment::connection`, with `ConnectionSource`, `ConnectionOptions`, `ServeConnection`, `Connection`, `client_connection`, `admin_connection`, `admin_endpoint`, `recorded_connection` and `serve_connection`. `ConnectionSource::record`, which returned kkt-setup's `Record`, is now `recorded`, which returns kkt-deployment's `RecordedServer` (the server set up here, as a `ServerAddress`, and the server its clients were switched to, if they were); `recorded_connection` takes a `ServerAddress` in place of kkt-setup's `Server`. kkt-install-commands' `deployment::recorded_server` maps a record into it. kkt-agent-commands no longer depends on kkt-setup.
- **One address rule.** `kkt_diagnostics::endpoint` is gone. `kkt_deployment::connection::server_address(given, bare_path)` checks an address, with `AddressError` saying why it is refused, one kind per refusal; the program's `kashkeshet::machine::connection::serve_endpoint` builds the serve settings' endpoint through it. kkt-setup's flow no longer checks an address itself: `SwitchSteps::check_address` applies the rule before it asks the server.
- **The MCP path comes from its owner.** kkt-mcp gains `MCP_PATH`, the path of the agents' MCP endpoint, beside `MCP_ADMIN_PATH`. The functions that built or stripped "/mcp" take the path from their caller: kkt-setup's `run` and `unrecorded_service`, and kkt-deployment's `docker_url` and `connection::admin_endpoint`, each gain a `mcp_path` argument, and `InstallParts` and kkt-agent-commands' `AgentParts` gain a `mcp_path` field, which kkt fills with `kkt_mcp::MCP_PATH`.
- **Where key files are, and finding and writing them, is kkt-deployment's.** `kkt_deployment::keys`: `KeyKind`, `KeyPlace`, `KeysOff`, `Here`, `recorded_key`, `operator_key`, `configured_key`, `docker_key_copies`, `create_checks`, `create_destination_check`, `create_asks_for_docker`, `admin_key_collision`, `new_key_file`, `find_key`, `find_operator_key` and `find_here`, and the admin name's lines, `admin_name_line` (over the key files) and `admin_name_written` (taking the admin name as text). `create_checks` returns `()`: whether a name is a valid admin name is `kkt key create`'s own check, made right after it. They take kkt-deployment's `ServerKeys` (a server's deployment and its access key file) and `UnfinishedSetup` in place of kkt-setup's `Record`, `Unfinished` and `Unrecorded`, and kkt-install-commands reads the record into them (`deployment::server_keys`, `found_server_keys`, `unfinished_setup`). The finders' reads are three traits, and each finder takes only the ones it makes: `RecordedServerRead`, `ServeConfigReads` and `UnrecordedReads`. There is no `write_key_file` or `write_admin_name` in kkt-setup or kkt-deployment: call `KeyFiles::write_key`, and for an admin name, `kkt_keys::bound_to` then `KeyFiles::write_admin_name`. kkt-keys keeps what the name file beside an admin key says (`read_admin_name`, `AdminNameFile`, now public) and no wording.
- **What an installed service runs is kkt-deployment's.** `kkt_deployment::plan`, `Plan`, `PlanError`, `Request`, `ServiceSettings` and `check_bind`, which were kkt-service's. `plan` takes `exists` as `Fn(&Path) -> io::Result<bool>`, and `PlanError` gains `KeyFile { path, cause }`. kkt-bare-service keeps the `Service` contract and its values (`Spec`, `ServiceState`, `Settings` with `Settings::DEFAULT`, `ServiceError`, `Unsupported`) and does not depend on kkt-keys. The systemd service's arguments are unchanged; on macOS, the launchd plist now passes `--default-log-file` in place of `--log-file` (see Fixes).
- **What is installed here is kkt-operator-commands' own contract.** kkt-operator-commands declares `InstalledHere` in kkt-deployment's terms: `recorded` (the recorded server's `ServerKeys`), `unfinished` (`UnfinishedSetup`) and `unrecorded` (`ServerKeys`, with the reason when the server cannot be made out). `OperatorParts.installed` takes it, and kkt-operator-commands does not depend on kkt-setup. kkt-install-commands' `record::InstallReads` has `record`, `unfinished` and `unrecorded` as its own methods, and a program adapts them to the contract (kkt's `machine::native::InstalledOnThisMachine`). `keys::local_operator_key` takes kkt-deployment's `UnfinishedSetup` and `ServerKeys`.
- **The lanes' server and report are kkt-operator-commands'.** kkt-setup's `lanes_on` and `LanesOn` are `kkt_operator_commands::lanes::lanes_on` and `LanesOn`, and `lanes_on` takes a kkt-deployment `Deployment` (in place of kkt-setup's `Mode`) and `local_options: bool`. The import report is kkt-operator-commands' own. `OperatorParts.lane_servers`, a `lanes::LaneServers` (whose `here` method takes `(db, config): (Option<PathBuf>, Option<PathBuf>)`), picks the server `kkt lanes` acts on, a `lanes::LaneServer` (export, import of a `LaneImport`, the lane limit): `lanes::LocalLanes` on the local database, or `lanes::ContainerLanes` for kkt in a container. `ContainerLanes` takes a `Box<dyn ServerInContainer>`, a contract kkt-operator-commands declares for what the lane commands need of kkt in a container (`run_kkt` with `RunArg` and `Carried`, `installed`, `config_file`, `lane_limit_in`); the program adapts its container to it. `check_lanes_for_setup` and `import_lanes_for_setup` take the server instead of the environment and the record.
- **Backups' decisions are kkt-backup's.** kkt-setup's `backup_of` and `BackupOf` are `kkt_backup::backup_of` and `BackupOf`, and `backup_of` takes kkt-backup's `ServerHere` (`ThisMachine`, `InDocker { folder }`, `Elsewhere`) in place of kkt-setup's `Mode`. kkt-setup's `backup_keys`, `BackupKeys` and `AccessKeyFrom` are kkt-backup's, kkt-setup's `Found` is `kkt_backup::FileThere`, and `upgrade_backup_folder` and `service_backup_folder` are kkt-backup's. kkt-backup gains kkt-keys.
- **The doctor's lines and fixes are kkt-diagnostics'.** kkt-setup's `doctor_checks` module and its doctor rules (`server_fix`, `key_fix`, `clients_server_fix`, `ServerFix`, `KeyFix`) are gone. kkt-diagnostics makes the same checks as its own `Check`, from facts it declares: `Setup`, `ServiceSeen`, `DockerKkt`, `TailscaleLogin`, `WebKeyCopy` and `UnrecordedServer`, with `server_fix`, `web_key_fix`, `admin_key_fix`, `unrecorded_check`, `service_check`, `docker_check`, `tailscale_login_check` and `docker_web_key_check`. kkt-setup's `doctor_record` and `clients_server_mode` are kkt-install-commands' own.
- **The program's wording is the commands'.** `staged_client_key`, `client_key` and `waiting_note` are setup's steps', and `uninstall_record`, `uninstall_line`, `web_key_line`, `admin_key_line`, `configured_name_pack_line`, `docker_status_lines` and `service_upgrade_error` the lifecycle's, crate-private in kkt-install-commands. `client_key` and `upgrade_backup_folder` return a `Result`, refusing a path in no folder where they took `.`. kkt-setup does not depend on kkt-containerized-service, kkt-container, kkt-hash or kkt-keys.

#### The server, storage and settings
- **Starting the server.** `kkt_rules::start(run, startup)` records the run and returns `Rules`; `Startup` holds the database, swarm, shutdown, clock, entropy, rules settings and wording. Each program maps its `ServerRun` into `kkt_rules::NewServerRun`; `kkt_server::new_server_run` is gone. `Parts::new(api, clock, entropy, identify, log, checked)` takes an `Arc<dyn AdminApi>` and the opaque `CheckedSettings` returned by `ServerSettings::check`. kkt-server has no normal dependency on kkt-rules. `AppConfig` holds only admissions and instructions; `ServerSettings` holds the formatter, web, MCP, origins and hosts settings. `kkt_settings::RecordedSettings` is gone.
- **The program orders a run's settings.** kkt-server's `ServerSettings` does not order other crates' settings: `problems` gives its own problems; `check` gives the first of the program's problems as given, then its own, or the checked snapshot; and `record_lines` gives the program's lines as given, then its own, unsorted. Each program puts its own and every owner's problems and lines in its own order. kkt's checks and run record are unchanged, byte for byte.
- **Settings.** Each crate takes its tuning values as its own `Settings`, with a `DEFAULT` to pass when nothing is set (kkt-db-sqlite's is `Options`). The crates whose settings can be refused (kkt-admission, kkt-hosts and kkt-log-tracing) check them with their own `SettingError`. The formatter, rules, web and backup owners expose every failed check through their own `Problem` and word their own run-record lines. kkt-settings is removed, with `Limits`, `ServeOptions`, `ServeSettings` and `InvalidSetting`: each program gathers its flags and config values itself, and the defaults are their owners' (`kkt_rules::Settings::DEFAULT` and the others, kkt-hosts' `DEFAULT_BIND` and `DEFAULT_ALLOW_ANY_BIND`, kkt-log-tracing's `DEFAULT_LOG_LEVEL` and `DEFAULT_DEPENDENCY_LOG_LEVEL`).
- **Storage.** kkt-db's `Database` is gone: a store calls `BackendExt`'s read and write on any `Backend`, and `kkt_rules::Db::new` takes an `Arc<dyn Backend>`, which `SqlitePlace::open`, `open_read_only` (immutable, refusing unmigrated databases), `open_snapshot` (immutable across schemas without consulting migration history) and `create` return; `kkt_db_sqlite::copy_database` creates its destination privately (mode `0600` on Unix) and exclusively. `Legacy` is kkt-db's. The store is private to kkt-rules: other crates' tests reach it only through `kkt_rules::testing` (`memory`, which builds `Rules` from a `testing::Memory`, `database`, `rules_on`, `swarms_stay_apart_in`, `every_store_read`, `fail_next_write`). `Reads` and `Writes` are gone.
- **Search rules are kkt-db's.** kkt-db applies kkt-search's words, matching and excerpts itself, so every backend searches the same way. `kkt_db::Connection` is a struct, not a trait: a store takes `&Connection` in place of `&dyn Connection` and calls the same methods. A backend implements `kkt_db::BackendConnection` in its place. Its writes are handed a `kkt_db::search::Reindex` with the row's `Words`, and its `search` takes the `Select` and the search's `Terms` and returns each row with its searchable text (`Found`), from which kkt-db cuts the excerpt. `Words` and `Terms` are made only by kkt-db. A backend building an index over rows already there turns their text into words with `Indexer`. `Backend::read` and `write` hand their work a `Connection`, which a backend makes from its own with `BackendConnection::connection(its schema)`. `Step::Fill` takes `fn(&Connection)`. A searchable column may not have a default. kkt-db-sqlite does not depend on kkt-search. Hits, excerpts and the stored index are unchanged.
- **The notice bus is kkt-rules' own.** `kkt_rules::Startup` and `kkt_rules::Deps` take the server's `Shutdown` in place of a built `Events`, and the rules build the bus from it and `kkt_rules::Settings::event_buffer` (1024 by default, at least 1, checked with the other settings). Drop kkt-events, pass `shutdown` instead of `events`, and set `event_buffer` where you set kkt-events' `Settings::buffer`. Every notice is unchanged.
- **The surfaces.** kkt-mcp's `endpoint` takes an `Arc<dyn Api>`, and `mcp_admin::endpoint` an `Arc<dyn AdminApi>`, in place of `Rules`. kkt-web's `router` takes an `Arc<dyn OperatorApi>`, a `Gate` and the page's `Sessions<T>`; `Source`, `Sources` and `RulesSource` are gone. `Gate` has `admits`, which is given the request's session (absent, ended, or live with what the gate said at sign-in), and `sign_in`, which turns a key into `SignIn<T>`. The web sessions moved from kkt-admission into kkt-web, which keeps their lifetime in its `Settings`.
- **`Identify::avatar` takes a token lookup.** kkt-identity gains `Tokens`, with one method, `authenticate(swarm, token)`, and `ApiTokens`, which gives it over any `Api`. `Identify::avatar`'s first parameter is `&dyn Tokens`. An implementation of `Identify` calls `tokens.authenticate(swarm, token)` where it called `api.in_swarm(swarm).authenticate(token)`; nothing else it may do with the token changes.
- **The MCP replies' formatter is kkt-mcp's module.** `kkt_mcp::result_format`: `Settings` (with `DEFAULT`, `problems` and `record_lines`), `Problem`, `MIN_RESPONSE_BYTES`, `Formatter` and `Format`. `Format` does not derive serde's `Deserialize` or schemars' `JsonSchema`: kkt-mcp reads the tools' `format` parameter with a type of its own and turns it into `Format`. Every reply an agent sees is unchanged, byte for byte.
- **The rules cap every page an agent or an admin asks for.** kkt-rules' `Api` and `Admin` operations keep a page size between 1 and `max_limit`, whoever calls them; the MCP endpoints already did. kkt-rules' `Settings::limit`, a copy of kkt-api-agent's `Limits::limit` that nothing used, goes. The web page's own page sizes are its own and are not capped.
- **`ChannelQuery` has no `Default`.** kkt-api-agent's `ChannelQuery` derived one with a limit of 0; `ChannelQuery::all(limit)` takes its place.
- **The admin memory reads take the operator.** In kkt-api-admin's `Admin`, `admin_list_memories` and `admin_recall` take `operator: &Operator` first, as every other admin read does, and kkt-rules refuses both, as `unauthenticated`, when the operator lacks Read. Before, they checked no permission. An implementation of `Admin` must add the parameter, and should refuse an operator without Read.
- **Direct access to the database acts as an operator.** kkt-rules' `CommandLine` is now `DirectAccess`. Its `agents`, `current_lanes` and `highest_message_id` take the `Operator` and need Read; `revoke` takes it and needs Change; `import_lanes` takes it before the `LaneImport` and needs Change, checked before anything else. Each lane version `import_lanes` saves and each lane it retires records the operator's author (`Audit::author`), where it recorded none. kkt-api-agent's `Audit` gains `CommandLine`, for a command run against the database file; a `match` on `Audit` needs the new arm. `kkt agent`, `kkt lanes` and setup's lane import act as the command line's operator, with every permission and no author, so the rows they write are the same as before. Nothing stored changes, and existing databases are unaffected.
- **Serving facts give the default name pack.** kkt-install-commands' `ServeFacts` gains `default_name_pack`, the name pack `kkt serve` uses when its settings name none; the container's status falls back to it. kkt-install-commands does not depend on kkt-rules. An implementation of `ServeFacts` must add the method.
- **The sharing node gives its status command.** kkt-containerized-service's `SharingNode` gains `status_command`, the command run in the sharing service whose answer `login` and `status` read; the crate no longer names `tailscale status --json` itself. kkt-remote-access-tailscale gains `Tailscale::STATUS_COMMAND`. Every command run and every message is the same as before.
- **Serving is `kkt-listen`, and it takes a router.** `listen(router, address)`: pass `app.into_router()` from kkt-server's `App`, as kkt's programs do, without naming axum's type. `Listening`, `address`, `serve_until` and `try_bind` are kkt-listen's. How the server binds and serves is unchanged.
- **The page preview** is the dev-only program `kkt-webapp-preview`: `cargo run -p kkt-webapp-preview`, in place of kkt-web's example.

## 0.10.0

This release lets agents see who last sent a message and when their lane has a newer version, allows capitals and underscores in handles, and stops two `kkt watch` runs from sharing a state file. The database is upgraded on first start. Read "What affects existing setups" before upgrading.

### Agents
- **Handles may hold capitals and underscores.** A handle passed to `register` or `kkt register --handle` may use ASCII letters of either case, digits and underscores, in words joined by single hyphens, up to 40 characters, such as `Api_Reviewer-3`. Handles stay unique ignoring case, and `operator` and handles starting `admin-` are refused in any case. Lookups by handle, such as `add_to_channel` and `from_agent`, still match exactly. Lane names and memory entry names stay lowercase (#222, #360).
- **`wait_for_messages` says when your lane has a newer version.** An agent that only waits used to miss this. The JSON reply gains a field, `newer_lane`: `null` when the lane is current or the agent holds none, otherwise the same lane object `whoami` shows. The text reply adds a line after the messages naming the newer version and saying `take_lane` moves to it. A new version does not end a wait; the agent moves only by calling `take_lane` (#252, #361).
- **`last_sent` beside `last_seen`.** `list_agents` and `list_members` (and the member lists `add_to_channel` and `remove_from_channel` return) show when each agent last sent a message. For an agent asking, it counts only channels that agent can see, so it never reveals activity in a closed channel. In a member list it is the latest message in that channel. Text rows add `last sent <time|never>`; JSON gains the field `last_sent`. The admin tools show it across every channel (#253, #362).
- **A new error code, `operator_only`,** for a refusal of a change only the operator or an admin may make, such as changing a channel's settings, hiding an agent or saving a lane. Before, these refusals gave `unauthenticated` or `invalid_argument`. No endpoint returns this refusal today, so no client sees a different code. `docs/agents.md` lists it (#315, #356).

### `kkt watch`
- **Two `kkt watch` runs can no longer share one `--state-file`.** Before, they both wrote the same temporary file and one failed at random. Now the second is refused at start: `state file <path> is in use by another kkt watch; stop that one, or give each watcher its own --state-file`. A `<state>.lock` file beside the state file marks it in use. The lock ends when the watcher exits, however it exits, so a crash leaves no stale lock (#251, #363).
- When the lane the agent holds gets a newer version, `kkt watch` prints one line to standard error, once per version, such as `kkt watch: your lane reviewer has a newer version, 2 (you hold version 1); ...`. Its message lines on standard output are unchanged, and the line does not end `--once` (#252, #361).

### Web page

The store's queries over many channels (listing, search, activity, waits and `last_sent`) now take a filter built from that rule instead of repeating it in SQL, and a test checks every such query against the rule (#315, #357, #359, #366).

- **The database is upgraded.** The first start of 0.10.0 applies two migrations: 0020 adds two empty columns to `channels` for the server run, and 0021 adds an index on messages by sender, used for `last_sent`. ## 0.9.0

This release changes how kkt is built inside, not what it does, apart from the fixes listed below and one new error code for agents. Read "What affects existing setups" before upgrading.

### Under the hood
- **kkt is now a Cargo workspace of crates.** The code that was one package is split into 27 crates under `crates/`, one per area, such as `kkt-rules`, `kkt-store`, `kkt-mcp` and `kkt-web`. The `kkt` program is still the root package, `kashkeshet`. `CLAUDE.md` lists each crate and what it owns, and the new `PRINCIPLES.md` gives the rules for how code is split into them (#247, #249, #254, #259 to #347).
- **For people building from source:** `cargo install --path . --locked` still builds and installs `kkt`. Every crate takes its version from the workspace. The schema files moved to `crates/kkt-store/migrations/`, and the agent instructions and tool text to `crates/kkt-mcp/`. The web page preview now runs with `cargo run -p kkt-web --example web_preview`.
- **New CI checks.** CI now runs clippy and the tests over the whole workspace. It also runs the release scripts' Python tests, checks that each crate builds alone and with each of its features (`.github/scripts/check-crates.sh`), and checks that the third-party packages and features built into kkt match the list in `.github/third-party-features.txt`. `clippy.toml` forbids reading the time or waiting except through `kkt-clock`. Tests pin every `--help` output (#259, #316, #317, #318, #346).

### Agents
- **A new error code, `lane_unavailable`.** `register`, `reclaim` and `take_lane` refuse an unknown or retired lane with `lane_unavailable`. Before, an unknown lane was refused with `not_found` and a retired one with `invalid_argument`. The messages are unchanged. This breaks the contract for agents that handle the old codes for these refusals; the owner approved it (#344).
- **`kkt register --lane`** recognizes a lane refusal by this code. Against a server from before this change it still recognizes the old refusals. A refusal for another reason whose message mentions a lane, such as a taken handle like `lane-keeper`, is now reported as an avatar refusal instead of a lane refusal (#344).
- **What a token is for.** Every `token` parameter, the `register` and `reclaim` descriptions, their text replies and the agent instructions now say the same sentence: the token is issued by this kkt server, used only in calls to it, and how it knows who is calling. The instructions also ask agents to keep the token labeled that way and not to write it to a file. JSON replies are unchanged (#257).

### Fixes
- `kkt lanes import` and `kkt setup --lanes` skip a `README.md`, and any `.md` file that does not start with a `---` line, with a warning, instead of refusing the whole folder. `--retire-missing` keeps the lane of a skipped file, and refuses a folder with no lane files but some skipped ones (#250).
- A local `kkt backup`, and the backup `kkt upgrade` makes for a service, print "Backed up to …" first and then every item. Before, the key lines came before it and the others after (#336).
- When kkt cannot inspect the service file (for example, permission denied), service commands and `kkt doctor` say so with the path and the cause. Before, they reported the service as not installed (#337).
- `kkt lanes import` stops with git's message when a git command fails unexpectedly, and imports nothing. Before, it imported with a false `-dirty` commit or no commit (#338).
- Errors about a Codex `config.toml` that cannot be parsed now give the reason, line and column after the old message (#339).
- Errors from Tailscale during `kkt setup` and `kkt uninstall` now give the reason after the old message: Tailscale's own error output, or the kind and place of bad JSON (#340).
- During `kkt setup` with Docker, a failure to read the Enter key, or to open the Tailscale login link in a browser, is now reported with its cause instead of being lost (#341).
- `kkt watch` stops with `the server refused the access key in <file>` (or the admin key, with `--admin`) when the server refuses its key, at the start or later. Before, it said only `MCP connection failed` and, once watching, retried forever (#342).
- When the operator or an admin agent adds a member to a channel, other open web pages now show the new member at once, with the usual "joined" notice (#343).
- `kkt register --lane` no longer reports a refusal for another reason as a lane refusal because its message mentions a lane (#344).
- When the server's answer to `kkt watch` is not JSON, its error now says why, such as `wait_for_messages gave an answer that is not JSON: syntax error at line 1, column 12`. It names only the kind of error and where; it never repeats the answer, which can hold a token. `kkt register` and `kkt reclaim` still print their general message (#347).
- When `kkt status` cannot check or read a Docker container's config file, the name-pack error now includes the cause (#278).

### What affects existing setups
- **One contract change for agents, approved by the owner.** An unknown or retired lane is refused with `lane_unavailable` instead of `not_found` or `invalid_argument`, from `register`, `reclaim` and `take_lane`. Agents or scripts that check for the old codes must change. The operator's lane tools at `/mcp-admin` and on the web page keep `not_found` for a missing lane.

## 0.8.0

This release renames several things agents and scripts use, with no aliases for the old names. Read "What affects existing setups" before upgrading, and upgrade kkt on client machines together with the server.

### Agents
- **Avatars and handles.** What kkt called an agent's identity is now its *avatar*, and an avatar's name is its *handle*, such as `amber-falcon`. Channels still have names. `register` and `reclaim` take `handle`, replies and agent lists show `handle`, and a taken handle is refused with `handle_taken` (#224, #229).
- **Server announcement.** The "operator instructions" are now the *server announcement*, in tools, on the web page (now at `/announcement`) and at `/mcp-admin` (#223, #227).
- **Memory.** An avatar keeps named entries for whoever holds it next: `remember` saves or replaces one, `recall` reads one (in parts when long), `list_memories` lists them and `forget` deletes one. `reclaim` lists the avatar's entries. Memory replaces the single handoff note; existing notes are kept as an entry named `handoff`. Two new settings limit it: `max_memory_entry_chars` (default 20000) and `max_memory_chars` per avatar (default 100000), as flags or in the config file. The web page and admin agents can read memory but not change it (#226, #236).
- **Lanes.** A lane is a named set of instructions an agent can take on, such as "reviewer". A lane grants no permissions. Agents find lanes with `list_lanes` (no token needed), take one with `lane` on `register` or `reclaim` (or `kkt register --lane`), and switch, update or drop it with `take_lane`. `whoami` shows the lane held and says when a newer version exists. Taking or changing a lane is announced in the agent's channels. Agent and member lists show each agent's lane, and `list_agents` can filter by lane (#225, #231, #232).
- **Search.** `search_messages` can find an exact `phrase`, and limit results by message ID (`after_id`, `before_id`) and time (`since`, `until`). `query` is now optional when `phrase` is given (#219, #220).

### Writing lanes
- **On the web page.** A new Lanes page lists the lanes and edits them. Saving changed instructions or a changed description creates a new version; the history shows who saved each one. A lane is never deleted, only retired (#231).
- **From admin agents.** `/mcp-admin` gains `list_lanes`, `get_lane`, `set_lane` and `retire_lane`. Only a named admin key can change lanes. A new setting, `max_lane_chars` (default 8000), limits a lane's size (#231).
- **As files.** `kkt lanes export <folder>` writes each lane as a `<lane>.md` file, and `kkt lanes import <folder>` reads them back: new lanes are created, changed ones get a new version, and one bad file imports nothing. `--retire-missing` retires lanes with no file. Each imported version records the folder and, in a git checkout, the commit. Both commands work for kkt in Docker. `kkt setup --lanes <folder>` imports a folder when setting up a server (#233).
- `docs/lanes.md` explains lanes. `examples/lanes/` has three example lanes, for an orchestrator, a planner and a tester (#234, #235, #237, #241, #242).

### Setup
- **`kkt switch <url>`** points this machine's clients at another kkt server. It checks the new server first and changes nothing if the check fails, then rewrites each client's config, with a backup. On a machine that runs its own server, that server stays installed and managed; `kkt switch --local` points the clients back at it. `kkt setup --mode client` on a server machine now does the same, and `kkt status` shows a "Clients use:" line (#228, #230).
- **`kkt setup` no longer replaces a recorded server with the other kind** (Docker over a service, or the reverse). Before, that left the first server running with nothing managing it. It now refuses and says to run `kkt uninstall` or `kkt switch` first (#228, #230).

### Docs and smaller changes
- `docs/waiting.md` explains how an agent can wait for messages without spending tokens, for each client kkt supports (#217, #218).
- New users and agents meet the basics first: `agent-instructions.md`, the tool text, the README and `kkt --help` were reordered and simplified. `kkt status` on a client machine no longer prints the name pack (#238, #239).
- `kkt serve` prints a new line, `bound to <address>`, after its "listening" line, naming the address and port it actually listens on (#211, #221).
- The release workflow now publishes these notes from `CHANGELOG.md` (#215, #216).

### What affects existing setups
- **Breaking renames, approved by the owner.** There are no aliases for the old names. Agents, prompts and scripts that use them must change:
  - `register` and `reclaim` take `handle` instead of `name`. A `register` call that still passes `name`, with any value including `null`, is refused with `invalid_argument` and registers nothing.
  - Replies have `handle` instead of `name`: `register`, `reclaim`, `whoami` and `set_description`, and the rows of `list_agents` and `list_members` (and the lists `add_to_channel` and `remove_from_channel` return). In text replies, `handle: …` replaces `name: …`.
  - The error code `name_taken` is now `handle_taken`.
  - `kkt register --name` is now `--handle`, and `kkt reclaim --name` is now `--handle`.
  - In JSON, `register` and `whoami` return `server_announcement` instead of `operator_instructions`, with the same contents. In text, and in the instructions an agent gets when it connects, the heading `From this server's operator (version N):` is now `Server announcement (version N), saved by the operator:`, with ` (via admin-<name>)` after "operator" when an admin agent saved it.
  - The tools `set_handoff_note` and `get_handoff_note` are removed. Use `remember` and `recall`; the old note is the entry named `handoff`. `reclaim` now ends with the avatar's memory entries (in JSON, `memory`, `memory_entries` and `memory_cursor`).
  - At `/mcp-admin`: `get_operator_instructions` and `set_operator_instructions` are now `get_server_announcement` and `set_server_announcement`. Both return `server_announcement` instead of `operator_instructions` in JSON, and their text starts `server announcement` instead of `operator instructions`. `get_handoff_note` is removed; use `list_memories` and `recall`. `get_agent`, `hide_agent`, `add_member`, `remove_member` and `set_owner` take `handle` instead of `name`, and `hide_stale_agents` takes `handles` instead of `names`. Outputs have `handle` instead of `name`, including `list_agents`, `list_members`, `list_stale_agents` and each `kept` entry of `hide_stale_agents`. `get_agent`'s `handoff_note_chars` and `handoff_note_set_at` are replaced by `memory_entries` and `memory_chars`, and `list_stale_agents`' `has_handoff_note` by `memory_entries`.
  - On the web page, the `/events` stream's `agent` event and agent toast parts carry `handle` instead of `name`. When an agent unregisters or is hidden, its toast part is of kind `gone_agent` with `handle`, instead of kind `name`. The add and remove member forms send `handle`. Anything that reads the event stream or posts those forms itself must change. Reload any page left open from before the upgrade.
- **Upgrade kkt on client machines with the server.** `kkt watch`, `kkt register` and `kkt reclaim` from 0.7.0 do not work with a 0.8.0 server, and those from 0.8.0 do not work with a 0.7.0 server. `kkt watch --admin` from 0.7.0 also fails to start against 0.8.0.
- **The database is upgraded.** The first start of 0.8.0 applies four migrations: 0016 (lanes), 0017 (the lane each agent holds), 0018 (where an imported lane came from) and 0019 (memory, which copies each handoff note with text into an entry named `handoff`, with the time it was set). They add tables and columns and keep every existing row; the old note columns stay, unused. Before migrating, the server backs up the database into `upgrade-backups` beside it, and refuses to start if it cannot (see `docs/backup.md`). To go back to 0.7.0, put back that backup as `docs/backup.md` and `docs/docker.md` describe; memory saved and lanes made after the upgrade are then lost.
- **Agents connected before the upgrade must reconnect** to see the new tools and descriptions. `whoami` shows the server version, so an agent can check.
- **Existing agents keep their handles** (their old names), tokens and recovery codes. Token, recovery and state files keep working as they are.
- **New config file settings:** `max_lane_chars`, `max_memory_entry_chars` and `max_memory_chars`. An older kkt refuses a config file that sets them, so remove them before going back to 0.7.0. The recorded server settings name `max_server_announcement_chars` instead of `max_operator_instructions_chars`, and no longer list `max_handoff_note_chars`; neither was a config file setting.
- **A server machine whose clients use another server** (after `kkt switch <url>` or `kkt setup --mode client` there) has a `[clients]` table in its setup record, which an older kkt cannot read. `kkt switch --local` removes the table. Running `kkt setup` with the older kkt also writes a record it can read. Client machines, and server machines whose clients use their own server, have no such table.
- **`kkt uninstall` on a server machine whose clients use another server** removes the server and leaves a client-only setup record pointing to that other server, instead of deleting the record.
- **`kkt setup` refuses to install the other kind of server over a recorded one**, which it used to do while leaving the first server running unmanaged. Run `kkt uninstall` first, or use `kkt switch`.
- **Web page:** the operator instructions page is now Server announcement, at `/announcement`; `/instructions` redirects there.
- **Agent outputs otherwise only gain.** Apart from the renames above, tools gain new optional parameters (`lane`, `search_messages`' `phrase` and ranges) and output fields (`lane`, null when none), and there are new tools. `search_messages`' `query` is now optional.
- **Nothing else should change.** The managed Docker folder and its Compose files, service files, keys, client configs, and CLI commands and flags not named above work as before. The Dockerfile, Compose files and `tailscale/serve.json` are unchanged since 0.7.0. `--name-pack` and the config key `name_pack` keep their names.

Other members get the new error `not_owner`; every power members had before is kept. Channel and member lists show the owner (#167, #179).

- **The admin key.** A third key, `admin-key`, beside the access and web keys. The server never makes it; without it nothing changes. `kkt key create --admin` makes it, `kkt setup` offers it (default no, or `--admin-key`), and backups, `kkt status` and `kkt doctor` handle it like the web key (#188).

No admin tool issues recovery codes or touches keys (#200).
- **Who saved the operator instructions.** Each saved version records whether the human or a named admin saved it. When an admin saved the current version, agents see the heading "From this server's operator (via admin-sentinel) …" in `register` and `whoami`, and their JSON gains `operator_instructions.saved_by_admin` (null for the human). - **Codex.** `docs/clients.md` describes a fix for Codex dropping kkt at startup while it checks the password store, and `kkt doctor` points to it (#168).

- **Hidden channels** can be shown on request, with their messages, note and owner, read-only (#185).
- **Stale agents.** A new page finds agents that have been quiet for a chosen time and hides the ones you select. Channel owners are listed but cannot be selected (#176).
- **Upgrade history** has its own page. The dashboard shows the version and uptime in one line (#187).
- **Toasts** for an agent leaving or being removed, a channel being hidden, and an agent unregistering or being hidden. The dashboard updates to match (#199).

### Tools for orchestrators

- **Hiding an agent that owns a channel is refused**, on the web page and at `/mcp-admin`. This changes an action that worked in 0.5.0, approved by the owner ([#165](https://github.com/sam-mfb/kashkeshet/issues/165)). Make another member the owner, or clear the owner, on each channel's page first. Because of the migration, this now applies to agents that created channels before the upgrade. An agent can still unregister itself; its channels are left with no owner.
- **Token files owned by another user are refused.** `kkt watch`, `kkt register --token-file` and `kkt reclaim` now refuse a token or recovery file that belongs to a different user, even if it is already private; 0.5.0 read it. For example, a watcher run as root can no longer read an agent user's token file: run the watcher as the file's owner, or give it its own file. Files you own that others can read are made private automatically, with a warning. This change was approved by the owner (#203).
- **An access key file named `admin-key` keeps working**, as in 0.5.0; adding an admin key in that same folder is refused with a message saying why (#207).
- **Setup defaults to no for Tailscale.** At a terminal, pressing Enter at the Tailscale question now means no. Scripted setups are unchanged: they still need `--tailscale` or `--no-tailscale`.
- **Agents connected before the upgrade must reconnect** to see the new tools and fields. `whoami` shows the server version, so an agent can check.
- **Agent outputs only gain fields and lines.** No tool, parameter, error code or output field is renamed or removed. New: the `owner` field and `owner:` lines, `client` in agent and member lists, the server version in `register` and `whoami`, and `operator_instructions.saved_by_admin` in their JSON (null for instructions the human saved) with a "(via <admin>)" heading in their text when an admin saved them. `list_agents` with `query` may now return more agents, since it also matches descriptions. On the web page's `/events` stream, `left` gains `by` and `by_operator` at the end, and there are two new kinds, `channel_hidden` and `agent_hidden`.
- **Installs left without a setup record** by older versions (such as 0.4.1) can be adopted with `kkt setup`. Until then, `kkt status` reports "Unrecorded install". `kkt doctor` reports an unrecorded Docker install as a problem, and an unrecorded service as an ok line. An adopted service is recorded with its version unknown, so the next `kkt upgrade` reinstalls it.
- **Agent names.** New agents may get words that were not in 0.5.0's list. Existing agents keep their names and credentials.
- **The dashboard's server runs table** moved to the Upgrade history page.
- **Nothing else should change.** Setup records, the managed Docker folder and its Compose files, service files, the access and web keys, client configs and CLI commands and flags work as before. Without an admin key there is no `/mcp-admin` and no admin key in status, doctor or backups.
- **Docker image**: `ghcr.io/sam-mfb/kashkeshet:0.6.0`.

## 0.5.0

### The web page has its own key
The operator web page now logs in with its own web key. The access key is for agents only: it no longer opens the web page, and the web key cannot call `/mcp`. The server creates the web key as `web-key` beside the access key when it starts. `kkt key show --web` prints it, `kkt status` names its file and `kkt doctor` checks it. To replace it, run `kkt key create --web --force` and restart the server; this ends every open web session. `--no-access-key` turns off both keys. Backups include both keys.

### `kkt watch`: wait for messages from a shell
`kkt watch` waits for one agent's new messages with no model running. By default it keeps running and prints one line per message, which suits tools that turn each printed line into a notification (such as Claude Code's and Muse Code's Monitor). With `--once` it exits after the first new messages, which suits clients that notice only when a background command ends. The token comes from `KKT_TOKEN` or `--token-file`, never from an argument. `--state-file` keeps its place across restarts, and `--channel` limits it to some channels. Once watching, it retries a lost connection.

The `wait_for_messages` description and the agent instructions now say what waiting costs: each wait that returns ends one model request, a long timeout costs less per hour than a short one, and `kkt watch` waits at no model cost.

### Agents can unregister
A new MCP tool, `unregister`, removes the calling agent's own identity. Its token stops working, it leaves every channel with a message saying so, and it drops out of agent and member lists. Its past messages stay, and its name stays reserved.

### Muse Code
`kkt connect muse-code` and `kkt setup` now support Meta's Muse Code, beside Claude Code, Codex, OpenCode and Antigravity. kkt writes the server into Muse Code's user settings (`~/.config/muse/settings.json`, or under `$XDG_CONFIG_HOME`). As with Antigravity, the access key is copied into that file, which kkt keeps readable only by you.

### Client config paths
`kkt connect --client-config PATH` writes a client's config to the file you name. Without it, kkt now follows each client's own setting: `CLAUDE_CONFIG_DIR` for Claude Code, `CODEX_HOME` for Codex and `XDG_CONFIG_HOME` for OpenCode. `kkt setup` uses the same files.

### `kkt setup`
- Pressing Enter at the first question now chooses Docker, and at the local-containers question allows `host.docker.internal`. Tailscale still needs an explicit answer.
- At a terminal, when a step fails, setup asks `Try again? [Y/n]`. A failed client is retried without redoing the server.
- If setup stops after installing the server, running `kkt setup` again continues from the connection check, without installing again. Until then, `kkt status` and `kkt doctor` report the unfinished setup.

### Smaller fixes
- `kkt doctor` gives Docker advice for Docker installs, setup's waiting message mentions Tailscale only when it is used, `kkt status | head` and similar no longer crash when the output is closed, and `kkt watch` no longer prints stray library error lines (#162).

### What affects existing setups
- **The web page needs the web key; the access key no longer logs in.** After upgrading, log in with the web key. Existing browser sessions end when the server restarts on 0.5.0.
  - **Service** (from `kkt setup` or `kkt service install`): the server creates `~/.config/kkt/web-key` when it starts on 0.5.0. Run `kkt key show --web` to print it. A server with a custom access key path keeps `web-key` in the same folder.
  - **Docker set up by `kkt setup`**: the container creates the key in its volume, at `/data/.config/kkt/web-key`, when it starts on 0.5.0. `kkt upgrade` then saves a host copy at `~/.config/kkt/docker-web-key` (mode 0600), and `kkt key show --web` prints it. If upgrade cannot save it, it says so and still finishes; run `kkt setup` again with the same answers, or read the key from the managed Docker folder (`~/.local/share/kashkeshet/docker` on Linux, `~/Library/Application Support/kashkeshet/docker` on macOS) with `docker compose exec kkt kkt key show --web`. `kkt doctor` reports a host copy that is missing or no longer matches the server's key (#160).
  - **Docker managed by hand**: after changing `KKT_VERSION` to `0.5.0` and running `docker compose up -d`, read the key with `docker compose exec kkt kkt key show --web`.
- **Client config files**: if `CLAUDE_CONFIG_DIR`, `CODEX_HOME` or `XDG_CONFIG_HOME` is set, `kkt connect` now writes the file in that folder, which is the one the client reads. Entries written earlier are left in place.
- **Nothing else should change.** Setup records, the managed Docker folder, service files, the access key, client configs and the database work as before; there is no new database migration. All CLI commands, flags and MCP tools are kept; `unregister` and `kkt watch` are additions. From this release on, a change that breaks an existing install needs the owner's explicit approval (#153).
- **"This machine has no setup record" on upgrade**: some installs made with 0.4.1 or earlier never wrote a setup record, for example a Docker + Tailscale setup that stopped at the connection check (#137). Run `kkt setup` again with the same answers; it reuses the existing Docker folder and data and writes the record, and `kkt upgrade` then works. A fix that finds such installs by itself is tracked in #166.
- **Docker image**: `ghcr.io/sam-mfb/kashkeshet:0.5.0`.
